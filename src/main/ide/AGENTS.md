# Embedded IDE

Detail for this part of the code. The root `AGENTS.md` holds the rules that apply everywhere (shipping checklist, cross-surface policy, logging, writing style); they apply here too.

## Embedded IDE (code-server) + file IPC

- **Right pane has three modes**: the terminal strip, the IDE pane (⌘⇧E toggles these two) and the HTML preview (`'preview'`, opened from a chat, never persisted; ⌘⇧E from it goes to the terminal). All stay mounted (positioned overlay) so xterm/pty, workbench and preview state survive toggling.
- `IdePane.tsx` renders the real VS Code workbench served by a per-app `code-server` process in ONE persistent `<webview partition="persist:ide">` - switching projects navigates the same webview to the new `?folder=` (RAM policy: never N workbench renderer processes). Prewarmed in the background once a session is active (server + hidden workbench; never downloads the binary uninvited), so the first ⌘⇧E is instant. Hidden 15 min → server killed + webview blanked; cold respawn ~0.35s.
- `src/main/ide/`: `code-server-manager.ts` (spawn args, release-asset table, extension seeding, lifecycle: EADDRINUSE retry-once, capped health poll, respawn after crash), `binary.ts` (download to `userData/code-server/<version>/`, PATH fallback for devs), `bridge-server.ts` (ws + token; routes open/selection by workspace folder).
- `resources/sb-bridge/`: zero-dependency extension seeded into code-server's extensions dir. `protocol.js` is pure (message build/parse/validate + reconnect backoff, unit-tested); `extension.js` is thin vscode glue (open-at-line, cmd+l selection capture, cmd+k quick edit, live config apply, the Switchboard Charcoal color theme (app palette), terminal-intent keybindings (ctrl+backtick / cmd+j / cmd+shift+e route to Switchboard's terminal pane; task/debug terminals untouched)). Ships via electron-builder `extraResources`.
- IPC (`IdeChannels`): `ENSURE` (boot + serve folder, TCC pre-flight per call) / `STATUS` (push: stopped | starting | downloading | ready | error) / `OPEN` (pill click → open-at-line in workbench) / `SELECTION` (cmd+l in workbench → chat draft pill) / `STOP` (idle shutdown).
- Security ADR: `--auth none` on `127.0.0.1` - same-user trust boundary as PTYs and the embedded SDK. Design doc: `docs/plans/archive/2026-07-10-embedded-ide-design.md`.
- Surviving file IPC (`FilesChannels`): `list-dir` (lean name/isDir - remote add-project autocomplete), `list-all` (@-mentions, 10k cap), `write-file`/`delete-file` (FileDiffCard accept/reject - atomic temp-then-rename, mtime conflict detection, 8 MB cap), `resolve` (inline file pill existence, plus `size`), `read-html` (one .html file's text for a remote chat's preview, 5 MB cap). `resolveWithinRepo` rejects `..`-escapes.

## HTML preview (`src/main/preview/`, `components/preview/HtmlPreviewPane.tsx`)

- An agent-written `.html` file opens in the right pane from the card under its Write/Edit call (`chat/HtmlFileCard.tsx`, rendered by `MessageList` after the work that wrote it, so a collapsed "Used N tools" group does not hide it) or from its inline file chip. Other files still open in the IDE.
- RAM policy, as the IDE: ONE `<webview>` reused for every file, unmounted after the IDE's idle time hidden (`ide.idleTtlMinutes`) or on Close, which releases the guest renderer and stops the folder watch.
- Sandbox, enforced in main whatever the renderer asks: partition `sb-html-preview` (not `persist:`); `will-attach-webview` strips the preload and forces sandbox, contextIsolation and no Node; `setWindowOpenHandler` denies; `will-navigate`/`will-redirect` keep the page on its own URL; permissions and downloads are refused; a dead SOCKS proxy plus `disable_non_proxied_udp` covers what never shows up as a web request. The global `web-contents-created` hook that opens IDE popups in the browser skips the preview session: a preview page could otherwise open any URL by logging the marker.
- Network: `session.webRequest` cancels everything except `sb-preview://<token>` (a fresh token per open, so a stale page loads nothing), `data:`, `blob:` and `about:blank`. The page also gets a CSP limited to `sb-preview:`; Chromium then reports most blocked requests as CSP console errors, which the pane turns into its "N blocked" list (`cspBlockedUrl`).
- Files: main opens a local file only inside the chat's folder (`resolveWithinRepo`, the same check `files:read-html` uses). `sb-preview://<token>/<path>` serves the document and files below its folder only (realpath containment, so symlinks out are refused). The folder, not the file, is watched (agents write through a rename) and a 250 ms quiet gap reloads the page.
- Remote chats: the renderer reads the file with `files:read-html` on that machine (`routing.invokeOn`) and opens it as content; no local path is involved, relative assets do not load and there is no live reload.
- Security tests: `tests/unit/html-preview-sandbox.test.ts` (policy) and `e2e/html-preview.e2e.mjs` (the real sandbox: a probe page tries the network, a popup, files outside its folder, Node and the app API).

## Inline live pages (```html-live, `shared/html-live.ts`, `chat/visuals/HtmlLiveFrame.tsx`)

- Same session, same sandbox: each inline frame is a `<webview>` in `sb-html-preview`, so every rule above applies unchanged. `PreviewController` keeps the pane's one document plus inline documents by token (`openInline` / `closeInline`, at most 16 kept); the request filter allows a URL whose host is any live token and blames a blocked request on the asking frame (`frameUrl`), else on the pane. A frame's document is `sb-preview://<token>/index.html` and nothing else by path.
- `/_sb/<path>` on any document's origin is a bundled library, never a file: only the `HTML_LIVE_LIBRARIES` paths, from `resources/sb-live` (extraResources `sb-live`; vendored unmodified, versions, licences and checksums in its README and `tests/unit/html-live-libraries.test.ts`) or, for `mermaid.js`, the app's own `mermaid/dist/mermaid.min.js`. A file doc gets them too, so a page saved with Save as file still draws in the pane. A version bump replaces the file and both checksum lists.
- `htmlLiveDocument` wraps a fragment (or injects into a full document's `<head>`): the `--sb-*` theme variables, `data-sb-theme`, an import map for `three` and `three/addons/`, and a size reporter that logs `__sb_live_height__:<px>`. The frame reads that line from `console-message`; anything else at error level is the error list, CSP reports the blocked list, as in the pane.
- Running rule (`pickRunningFrames`, `services/html-live-frames.ts`): at most two per window, the newest in view or started with Run. A frame runs only when closed, in view, under 128 KB, with known libraries, not in the pane and not saved. Open in pane is `HtmlPreviewTarget.live` (`preview:open` kind `live`); the frame shows In pane meanwhile.
- Still image: 1 s after load with no height change, main captures the guest (`preview:inline-capture`, PNG, JPEG when over the 4 MB cap) and the renderer stores it on the chat's backend (`html-live:update`, keyed by the hex SHA-256 of the block source, `db/html-live-pages.ts`, 300 rows). Phones read it with `html-live:load` (`html_live_images_v1`) and never run the page; `html-live:update` is admin-scoped, so a phone cannot change what other phones see. Open on desktop (`html-live:open-on-desktop`) pushes `html-live:open-request`, which a desktop window opens in its pane (`services/html-live-open-requests.ts`).
- Security tests: the inline block in `tests/unit/html-preview-sandbox.test.ts` and `e2e/html-live.e2e.mjs` (a probe frame tries the network, loopback, file:// and parent files, an unknown `/_sb/` name, a popup and navigation, and checks Node and the app API).

- The real-filesystem preview watcher test primes the folder watch until a setup asset write is observed before measuring bursts. On macOS a write immediately after `fs.watch` returns can be lost; a longer event timeout alone does not establish readiness. Keep exact event counts after a quiet interval for each measured burst.
- `startBridgeHost` seeds settings.json without awaiting it (`void patchWorkbenchSettings`). A test that starts it must wait for that write before the test ends (`ide-bridge-host.test.ts` wraps the real function and awaits it in `afterEach`). Otherwise the write logs after the worker closes, and vitest reports `EnvironmentTeardownError` even when every test passed.
