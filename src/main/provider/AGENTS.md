# Provider bridge

Detail for this part of the code. The root `AGENTS.md` holds the rules that apply everywhere (shipping checklist, cross-surface policy, logging, writing style); they apply here too.

## Provider bridge (`src/main/provider/`)

- `types.ts` re-exports from `src/shared/provider-events.ts` so renderer can type the IPC boundary
- `ProviderKind = 'claude' | 'codex' | 'opencode' | GenericAcpAgent` (`'gemini' | 'vibe' | 'cline' | 'copilot' | 'acp-command'`, `shared/acp-agents.ts`; the same string is the agent type on conversations and provider instances)
- `ProviderAdapter` interface - required: `startSession(opts, onEvent)`, `sendTurn(threadId, message, runtimeMode?, images?)`, `interruptTurn`, `respondToRequest`, `stopSession`, `setRuntimeMode`, `isAvailable`. Optional: `setModel?`, `answerQuestion?`, `listSkills?`, `cancelQueuedTurn?`, `promoteQueuedTurn?`
- **`policy.ts` is the shared policy module** (2026-04/05 - was previously inlined in claude-adapter). All three adapters import from it:
  - `decidePermission(mode, toolName) → 'allow' | 'deny' | 'prompt'` - pure, unit-tested
  - `denialMessage(mode, toolName)` - human-readable denial reason
  - `PLAN_READ_ONLY_TOOLS` - Read/Glob/Grep/NotebookRead/WebFetch/WebSearch/TodoWrite (+ Codex equivalents `read_file`/`list_files`/`search_files`/`fetch`) allowed in plan mode, everything else denied
  - `CUSTOM_UI_TOOLS` - AskUserQuestion + ExitPlanMode (+ Codex `ask_user_question`/`exit_plan_mode`) skip `tool.started` emission so the custom cards render instead of raw JSON
- `event-bus.ts` - `RuntimeEventBus` (EventEmitter) decouples adapter event emission from the renderer, so N subscribers (renderer, future telemetry) can listen instead of 1:1 `webContents` coupling
- `env-overlay.ts` - merges a provider-instance env overlay into the spawn env (skips empty strings so partial configs don't blank defaults)
- `claude-session-migrate.ts` - copies Claude SDK session JSONL across `oauth_dir` when rotating provider instances mid-flight, so resume survives a credential switch
- **Claude Agent SDK upgrades (0.3.296 since 2026-10-11).** Read the SDK CHANGELOG between the versions before a bump. One change from 0.3.260 to 0.3.296 matters here: from 0.3.286 an omitted `permissionMode` is left to the CLI's settings (`defaultMode`, or auto mode on third-party providers), so `queryOptions` must always pass one, as it does. Remote machines install the same version (`provision-deps.ts` reads it from `package.json`).

## Runtime events (wire format)

Defined in `src/shared/provider-events.ts`. Discriminated union:

- `content` · streaming text, `streamKind: 'assistant' | 'reasoning' | 'plan'`
- `tool.started` · tool call begun (skipped for custom-UI tools)
- `tool.completed` · tool finished
- `tool.denied` · **2026-04-20**: `canUseTool` hard-denied (e.g. Plan mode blocked Write) - UI renders denial pill
- `request.opened` / `request.closed` · approval prompt flow (`requestType: 'command' | 'file' | 'tool'`). Optional `reason` is why the provider asked: Claude fills it from `canUseTool`'s `decisionReason` and `matchedAskRule`, and every client shows it as a Reason line. In full access, and for an edit tool in accept-edits, an ask with `matchedAskRule` or `decisionReasonType: 'safetyCheck'` (the SDK passes that field at runtime but leaves it out of its types) gets a card instead of the mode's allow; every other allow stands, and plan keeps its read-only allows. Such a card has no timeout and does not wake a hub parent (follow-up: hub wake when a child opens a card)
- `turn.completed` · turn ended, with `costUsd? / usedTokens? / maxTokens? / numTurns? / durationMs?`
  - `limit?: { limitClass: 'usage_limit' | 'context_full', resetAt }` (`shared/limit-resume.ts`): the turn ended on a usage limit or a full context window; absent means neither. Claude sets it from a `rate_limit_event` rejection (any rejection is a usage limit, `resetsAt` seconds to ms) or a prompt-too-long `result`, and keeps it until the next turn starts. The rejection ends the turn, so the late empty `result` that follows it publishes no second `turn.completed` (each end settles one outstanding turn in the registry). Codex reads `codexErrorInfo` (and a 429 or "usage limit" in the message) of the final `error` notification and the failed `turn/completed`. ACP agents never set it: an unknown quota error stays a failure. Fixtures: `tests/fixtures/limit-classification-cases.json`. The CLI's `<synthetic>` model name is never recorded as the model (`reportedModel`)
- `turn.queued` / `turn.dequeued` · a `delivery: 'queue'` message is held until the running turn ends / left the queue (`started | promoted | cancelled | dropped | failed`), keyed by its chat row id (`echoMessageId(origin)`). The registry's `QueuedTurnLedger` fills in the text and serves list / promote / cancel (`turn_queue_controls_v1`); outstanding-turn accounting for a queued message is settled on `turn.dequeued` only, never in the IPC handlers
- `turn.queue-held` · after Stop (all three adapters, reason `Stopped.`), a failed or usage-limited turn, or a queued message that could not start (`turn.dequeued` `failed`, which stays listed as Not sent until Cancel), the adapter starts nothing more until the user resumes (`provider:resume-queued-turns`) or cancels. Claude takes held messages back out of the CLI queue (`cancelAsyncMessage`) and pushes them again, with a fresh uuid, on Resume. Clients keep queued rows on `status: error`; only `stopped` clears them
  - **Claude turn boundaries.** A queued message started at a `result` makes the status `running`, not `idle`. A steer sent mid-turn carries a uuid; when one was sent and a queued message waits, the next turn is undecided (`awaitingNextTurn`) until its first `message_start`, whose `user_message_uuid(s)` stamp names the queued message (it starts, with its mode) or the steer (a turn of its own). No stamp (an older CLI) means the queue head, as before. A turn nobody started (that late steer, or the agent's own follow-up) is announced as `status: running` with `newTurn: true`, which the registry counts until its `turn.completed`. A query that dies mid-turn ends the running turn itself (`endTurnWithoutResult`)
  - **Codex stale ends.** A `turn/completed` for another turn than the running one (the turn Stop interrupted, arriving after the next send started a turn) is ignored: no `turn.completed`, no idle status, no queue start
  - **Codex native queue: tried and rejected (spike 2026-09-29, Codex 0.158).** Its `thread/queue/*` methods are experimental, and they cannot carry our semantics: `queue/start` refuses while a turn runs, so Send now (promote into the running turn) has no equivalent; queue items carry no settings, so a queued message's own runtime mode cannot apply when it starts; and the server starts the next item itself, so a failed start cannot be reported back. Decision: Codex keeps going through our `QueuedTurnLedger`. Re-check only once the queue leaves experimental, can merge an item into a running turn, and stores per-item settings.
- `status` · session status change · `session` · sessionId recorded
- `context_window` · live token count (polled after each turn)
- `model.variants` · available model variants + current selection
- `plan.proposed` · ExitPlanMode intercept → PlanCard
- `question.asked` / `question.answered` · AskUserQuestion intercept → QuestionCard
- `file.edited` · **2026-06-02**: one event per changed file per turn, sourced from a git checkpoint diff (provider-agnostic) - drives the in-chat diff card with per-hunk accept/reject
- `request.expired` · the provider can no longer take an answer for an open approval or question (its session errored, stopped or restarted). Clients replace the card with a notice naming the reason, recovery closes cards the backend no longer lists, and `RESPOND_TO_REQUEST` / `ANSWER_QUESTION` refuse a request the registry no longer holds (`REQUEST_EXPIRED`) instead of returning silently
- `error` · adapter-level error surfaced to chat

## Auto-resume after a usage limit (flag `limit_auto_resume`, 2026-10-22)

`limit-resume.ts` (`LimitResumer`, one per production registry; tests that inject adapters pass `limitResume = true` to get one) runs the pure rules of `shared/limit-resume.ts`. The registry calls `onTurnEnded` after it publishes each `turn.completed`, so a usage-limited end with a reset arms the root conversation's `limit_resumes` row with a new request id and one timer at the reset plus a minute (rebuilt by `start()` at construction). The fire checks the cheap things first and reads usage (`fetchInstanceUsage`, unforced, so it can share the 45 s cache) only when they pass; a reading it cannot use counts as open, since the turn itself is the test. It sends `limitResumeTurn()` through `sendApprovalResultTurn` (no `turnDepth` reset, no link renewal) and then `resumeQueuedTurns`, so the held queue runs behind the resume turn in enqueue order. Traps:

- The fire waits while a turn runs or is being prepared (you sent one): that turn's end decides, and the fire tries again in 5 minutes. A normal end before the reset disarms with `ran`; another limit arms again. "Runs" is the session status, not `hasOutstandingTurn`: messages held behind the limited turn stay counted there, so the resume turn is sent with `queueBehindTurn: false` and the held queue follows it. `sendApprovalResultTurn` counts it as its own outstanding turn from that flag, not from the count. `busy` is read again after the usage reading, since a turn you send during the reading decides. `tests/unit/limit-resume-e2e.test.ts` drives the whole loop through the registry.
- Claude ends carry no turn id. A second limited end with the same reset within 30 s is the same turn, so it never re-arms a row Stop disarmed in between (the adapter no longer sends the late empty result's end; this guard stays for any other repeat). A new limit starts the streak at 0.
- A chat with no running session at fire time waits for `onSessionStarted` (called with the held approval result flush). The runner never starts a session itself.
- Disarm is durable: `INTERRUPT` (the Stop button) disarms `stop`, `notifyConversationArchived` disarms `archive`, the row's Cancel `cancel`. `STOP_SESSION` does not: closing a chat or switching agents also sends it.
- The resume turn's block is dropped by `splitSyntheticUserText` (and the Kotlin port); the chat shows the stored `[[sb:limit-resume]]` row, published live on `limit-resume.changed` with the row's `state` (`LimitState`).
- Measured: every fire ends a `limit-resume.fire` perf span with its outcome (threshold 0, so all are logged); `limit resume armed`, `not armed`, `disarmed` and `outcome` info lines count arms, skips, disarms and resume success.

## Subagent steps (2026-10-12)

A Claude subagent's work belongs to the Agent/Task call that started it. The adapter passes the SDK's `parent_tool_use_id` on as `parentToolCallId` on that subagent's `tool.started`, `tool.completed` and `content` events, and the tool-use id on `task.notification` (`toolUseId`, written into the notice text as `<tool-use-id>`). A subagent's `stream_event` frames are dropped (they would land in the parent's open message), and its blocks never touch the parent's `currentMessageId`, since a background subagent runs while the parent streams. The SDK forwards a subagent's text only with `forwardSubagentText`, which is off, so live rows hold its tool calls and notices.

- **One rule places them**: `shared/subagent-steps.ts` (`groupSubagentEntries`, `subagentView`; Android `SubagentSteps.kt`, both run `tests/fixtures/subagent-cases.json`). A step goes under its topmost Agent/Task call, so a subagent's own subagents flatten into it; a notice whose tool-use id is the agent call itself is that background agent's completion. A step whose agent is not in the feed (a history window) stays at the top level.
- **Status**: an error result is a failure; a result is done, unless it is the "Async agent launched" placeholder of a background agent, which waits for its completion notice. Duration and step count come from the `<usage>` block the CLI appends to a finished agent's result.
- **Reload**: the SQLite mirror stores `parentToolCallId` and `isError` inside the tool row's JSON (no migration), `mergeConversationMessages` carries them onto the transcript's call, and `loadConversationHistory` reads Claude Code's per-subagent transcripts (`<session>/subagents/agent-*.jsonl`, linked by `toolUseId` in `agent-*.meta.json`, `agent/subagent-transcripts.ts`) for chats Switchboard did not run. The JSONL parser keeps an Agent/Task call's result and every call's error flag; other outputs stay out.
- **Codex and OpenCode**: not mapped. Codex runs a spawned agent as its own thread (`collabAgentToolCall` names it in `receiverThreadIds`), so its steps are not items of the parent turn; following child threads is a separate change. OpenCode's ACP stream carries no child-session updates.

## Image pipeline (2026-04-20)

1. User pastes/drags image in `ChatInput` → `ImageAttachment[]`
2. `ChatPanel.handleSend` shrinks each `File` to a data URL with `fitImageToBudget` (canvas). Every client resizes the same way, by `src/shared/image-resize.ts` (Android port `domain/composer/ImageResizePlan.kt`): at most `MAX_IMAGE_LONG_SIDE` (2000 px, the Claude API limit once a request holds more than 20 images; Claude Code keeps earlier images, so one larger image breaks every later turn) on the long side, JPEG 0.85 (a PNG stays PNG while under 1 MiB), stepping down to 1600 px and then 1280 px at 0.75 until the image fits what is left of the 3 MiB message limit, which is unchanged and still enforced by `validateUserMessageImages`. A GIF is sent as is or refused, also when it is over 2000 px (re-encoding would drop its animation). The desktop composer takes the type from the extension when the MIME type is missing or `application/octet-stream`, and turns HEIC/HEIF into JPEG through `app:convert-heic` (desktop-only IPC, macOS `sips`, `main/heic.ts`; elsewhere the image is refused at send as unreadable). The decoder applies EXIF orientation and the output carries no EXIF. Each refusal names the image (`imageRefusalMessage`). The Expo app does it with `expo-image-manipulator` (a native module: added 2026-10-03, so it needed a new binary, not an OTA); Android with `BitmapFactory` and `inSampleSize` (`BitmapImageShrinker`) on the composer worker, when the image is staged into the draft
3. `providerApi.sendTurn(..., messageImages)` passes through preload → `provider-registry` IPC → adapter. Both registry entry points (`SUBMIT_USER_TURN`, legacy `SEND_TURN`) pass the images through `fitImagesToProviderLimit` (`image-limits.ts`, pure JS `jpeg-js`/`pngjs`, so the headless server runs it) before the adapter: a PNG or JPEG over 2000 px is shrunk in its own format (a JPEG turned upright from its EXIF orientation first, because the new file has no EXIF), a larger GIF or WebP refuses the turn by name. This catches older phone builds and re-sends of stored images. The stored turn and its hash keep the images as sent
4. Claude adapter strips the `data:image/png;base64,` prefix and builds `{type:'image', source:{type:'base64', media_type, data}}` content blocks alongside text
5. Codex adapter encodes images into JSON-RPC content blocks (Phase B done - see `codex-adapter.ts` `sendTurn`)
6. On JSONL reload, `JsonlParser.extractImages` reconstructs data URLs from image blocks - historical images survive restart

## Composer file attachments (2026-10-27)

Any other file is not sent as bytes. The composer copies it to `<userData>/attachments/<uuid>/<name>` (`src/main/attachments.ts`, 50 MB limit, copies older than 30 days pruned at startup) and adds a `file` pill whose content is the line from `attachmentPromptLine` (`src/shared/attachments.ts`): `[Attached file "x" is saved at: /path]`, or `[Attached folder "x" is at: /path]` for a dropped folder. The line reaches every adapter as text. The Claude adapter also sends each such PDF that is inside the attachments folder as a `document` block (`attachedPdfBlocks`, 10 MB and 100 pages for all of a turn's PDFs, and only when the page count is known), read synchronously so back-to-back turns keep their order. Phones send the bytes instead: `app:upload-attachment` (`{ name, data }` base64, 10 MB, capability `attachment_upload_v1`, registered on every host) saves the same copy and answers its path, and the phone builds the turn with `attachmentTurn` (the desktop's lines, tokens and file pills).

## Question / Plan flow

1. Agent calls `AskUserQuestion` or `ExitPlanMode` (both in `CUSTOM_UI_TOOLS`) - raw `tool.started` is suppressed
2. SDK fires `canUseTool` → our handler intercepts, emits `question.asked` / `plan.proposed`
3. ChatPanel appends a message with `question` or `plan` attachment
4. `MessageBubble` routes to `QuestionCard` (one question at a time, numbered shortcuts 1-9, auto-advance) or `PlanCard` (markdown + Implement/Iterate buttons)
5. User answers → `provider.answerQuestion(threadId, requestId, answers)` resolves the blocked Promise
6. `canUseTool` returns allow + `updatedInput` with the answer payload

## Sender line (2026-10-21)

`submitClientUserTurn` (SUBMIT_USER_TURN and the legacy SEND_TURN) puts one `<switchboard-sender>` line in front of the text the adapter gets: surface, device, the machine that runs the agent, whether its localhost reaches the user (`shared/sender-line.ts`, `sender-context.ts`, from the request context the host set, never from the turn), and up to three dev server addresses that terminals in the chat's folder printed (`terminal/dev-server-watch.ts`, fed by `PtyManager`, dropped when the PTY exits). A line the client sent is stripped first. The stored turn never holds it; the JSONL parser and the session scanner strip it on read, so no client sees it. No line for a slash command or for a turn the backend sends itself. A test fake that asserts exact provider text strips it with `stripSenderLine`. Plan: `docs/plans/2026-10-21-sender-line.md`.

## Cross-session messaging (`/send-to` + agent-initiated sends)

One session hands a self-contained summary to another on the SAME backend. Two entry points, ONE delivery method - `ProviderRegistry.deliverPeerMessage(input)`:

- **User-typed**: `/send-to <session>: <message>` (parsing + fuzzy target resolution in `renderer/components/chat/send-to-command.ts`) → `ProviderChannels.DELIVER_PEER_MESSAGE` → the registry with `initiator: 'user'`. The handler FORCES the initiator; a client claiming `'agent'` would take the agent path's budget while skipping the approval that path relies on.
- **Linked sessions**: `/link <session> [messages] [time]` / `/unlink [session]` (`renderer/components/chat/link-command.ts`, targets resolved like `/send-to`, and `/link` gets the same chat picker) let two sessions' agents message back and forth under the link's own budget (see the guard table). A trailing number is the budget and a trailing `Nm` / `Nh` the time (10 minutes to 24 hours; a unit is required, since a bare number is the budget), unless the text with them is exactly a chat's title ("Issue 172", "Sprint 2h"): options are peeled off only until an exact title matches. No time means the backend setting `chat.peerLinkDuration` (Settings > Chat & agents > Link duration, `30m` by default, stored in the `/link` form and read by the registry at link time; `peerLinkDurationChoice` turns anything that is not one of the row's choices into `30m`, for the row and the registry alike).
- **Agent-initiated (all three agents)**: `list_agent_sessions` and `send_agent_message` on the Switchboard MCP server (see `src/main/mcp/AGENTS.md`), so Claude sees `mcp__switchboard__*`, OpenCode `switchboard_*`. Names, descriptions and handler behaviour live in `provider/peer-tools.ts`; `mcp/peer-mcp-tools.ts` binds them to the server and applies the gate.

Delivery is an ordinary `sendTurn`, which is what makes a peer message structurally unable to answer an approval: nothing on the path reaches `respondToRequest`. The receiving body is `wrapPeerMessage`, which tells the peer the message is not from the user and carries no authority.

Guards, all pure in `shared/peer-messaging.ts` and held by the BACKEND so every client shares one budget:

| Guard | Value | Why |
|---|---|---|
| Body cap | 16 KiB | A peer message is a summary, not a transcript |
| Per-pair rate | 5 / 60s | Both initiators |
| Dedupe | identical (from, target, text) inside 10 min | Content-addressed id `pm_<16 hex>` |
| **Hop depth** | `PEER_MESSAGE_MAX_HOP_DEPTH = 1` | Agent sends only. Depth counts consecutive AGENT hops since the last human message, so a session acting on a peer message cannot pass one on: that is the A -> B -> A guard, and rate limits do not substitute for it |
| **Per-sender budget** | 6 / 10 min per SENDING session | Agent sends only. The per-pair limit is multiplied by fan-out otherwise (5 siblings = 25/min) |
| **Session link** (`shared/peer-links.ts`) | Per EDGE (both directions): the messages the user chose (`/link <session> [messages] [time]`, default 20, 1 to 200) or the edge's own window (the time given, else the Link duration setting, 30 min by default; 10 min to 24 h), whichever first. The edge stores its window: a message the user types in either session, or sends along the edge, renews both with it; Extend adds 20 (never past 200) and restarts that window, not the default | Agent sends along a link the USER made skip hop depth and the per-sender budget, so two agents can hold a back-and-forth and a hub can fan out to any number of linked workers (no cap on links per session). Only along that edge: the same session sending to an unlinked one meets both limits. Body cap, dedupe and per-pair rate still apply. 200 is ten default budgets. The window bounds time and the budget bounds volume: at the per-pair rate a busy pair spends 200 in about 20 minutes, so a long window keeps a sparse exchange alive but a chatty one still stops for the user. Kept at 200 when windows grew to 24 h for that reason |

Traps:

- **The gate is the server's, not the adapter's.** `peer-mcp-tools.ts` runs `decidePermission` on `mcp__switchboard__send_agent_message`: denied in plan (with a `tool.denied` pill), sent in full access, one ordinary approval card otherwise. The adapters let every `switchboard` tool through without a prompt of their own. `list_agent_sessions` runs unasked: it reads only titles the sidebar already shows, and prompting for a harmless read trains the user to click through the send that follows.
- **Hop depth is NOT cleared at turn end**, only by a user turn (set to 0 in `SEND_TURN`) or `STOP_SESSION`. Clearing it per turn would let an unattended chain continue by waiting. A Switchboard result turn (an approval card's answer, see `src/main/mcp/AGENTS.md`) does not clear it either, and does not renew a link.
- **Refusals go back to the model as tool output with `isError`, never as a throw** - a thrown MCP error reaches it as an unreadable transport failure and it retries the same call.
- The per-pair limit (5) is LOWER than the per-sender budget (6), so any test of the budget must fan out over two targets or the pair limit fires first.
- **Links are edges, user-made, in memory.** `/link A`, `/link B` from a hub makes two edges; A and B are not linked with each other. Only `ProviderChannels.LINK_PEER` creates one (`PeerLinkBook.link` refuses an `'agent'` initiator, and no MCP tool reaches it). Keyed by `resolveRootThreadId`. Removed by `/unlink`, by `STOP_SESSION` on either side (not by a profile switch, which restarts the session) and by archiving either chat (`notifyConversationArchived`). Not persisted: a restart stops every session, which would remove them anyway. `list_agent_sessions` reports `linked`, and `provider:peer-links-changed` (`{ threadIds }`, root ids) drives the desktop banner (`PeerLinkBanner`).
- **A link skips the hop limit, it does not reset it.** The receiving turn's depth still grows with each linked hop, so a session deep in a linked exchange cannot send to an UNLINKED session until the user speaks to it, and unlinking mid-exchange can leave both ends unable to send. That is deliberate: the link is consent for that edge only.
- **A link out of time holds the message** (`shared/peer-held-messages.ts`). An agent send refused only because the edge's window ran out is not refused: the registry keeps it (`peer_held_messages`, `db/peer-held-messages.ts`, so a restart, which removes every link, keeps it too), writes the Not delivered row with `held: true` ("Held for X until the link is renewed", Send now still works), and tells the agent it is held and not to send it again (not an error). At most 3 wait per sender and target (`PEER_HELD_PER_EDGE_MAX`); past that a send is refused as before, so a renewal never releases a flood. It goes out when the edge is renewed (charged to the edge, like any linked send) (a message typed in either chat, Send along it, `/link` again, Extend) or the target chat's session next starts (uncharged, skipping the per-sender checks it already met), and is retried after the target's turn ends while the edge is live; the row then reads "Delivered to X after the link ran out". A hand Send drops the hold (and is refused while Switchboard is delivering it, so it never goes twice). An unlink or an archive releases the holds on that edge: the row turns into an ordinary `link-removed` Not delivered row and nothing goes out on its own. A stop does not, since the target's next start is a delivery trigger. A spent message BUDGET still refuses, as below: the time window bounds how long agents may talk unattended, so a held message waits for the user rather than for the target's next turn (that would let two agents keep talking forever).
- **A spent budget never loses the message either.** The refusal tells the model the message was NOT delivered, to keep working, and to put it in its final reply. The registry also stores it in the SENDER's chat as a `[[sb:peer-undelivered]] <json>` system row (`PEER_UNDELIVERED_MARKER_PREFIX`, `PeerUndeliveredRow`) with a Send button, which delivers it as a user send (renewing the edge) and rewrites the row as sent (`rewriteSystemMarker`, carried by `undeliveredId`). The first refusal after a run-out publishes `peer.undelivered` with `notify: true`, which the push notifier (`kind: 'link'`) and the desktop (`notifyPeerLinkSpent`) turn into one notification naming both sessions; later refusals are rows only, until the edge is renewed.
- **Every client renders every `[[sb:` system row, and an unknown kind never shows raw.** The phones read stored rows through `shared/system-markers.ts` (`systemRowView`; Android `SystemMarkers.kt`, both run `tests/fixtures/system-marker-cases.json`): Not delivered gets its own row with Send (`provider:deliver-peer-message` is open to a phone's `chat` scope), the other markers a notice in the desktop's words, an `Error:` row an error, and a kind they do not know a neutral "Switchboard notice" (the desktop's `MessageBubble` falls back the same way). Android stores both from history and from the live `peer.undelivered` / `approval.result` events as `RawNotice` rows of type `history.system` with id `h-<messageId>`, so a reload and a live event land on one row and a sent update replaces it. A NEW marker kind needs a case in that fixture and a row in both ports, or it shows as the neutral notice.
- **Each edge keeps its own window.** `PeerLinkBook` stores `windowMs` per edge, so renewals and Extend restart that edge's length, never the current Settings default; changing Link duration affects only links made after. `/link` on an already linked pair replaces its budget and window (no time means the setting's), and the expired refusal names the edge's own length ("This link's time (4 hours) is up."). The banner shows the time left per link (`Worker A · 7 of 20 · 3h 12m left`).
- **Phones may unlink, never link or extend.** `provider:link-peer` and `provider:extend-peer-link` are admin-scoped in `device-auth.ts`: a link is consent to card-less agent traffic in auto mode, like approving a host write. `provider:unlink-peer` and the list stay open, since they only take power away or read.
- **Card along a link**: auto mode sends without one (the user lets the agent settle routine calls there, and a card per message would undo the link); sandbox and accept-edits keep the card, plan still denies, full access already sends. A card-less send carries `requireLink`, so an unlink while it is in flight refuses it instead of delivering it uncarded.
- **Lineage edges** (flag `hub_children`). Each open child (phase `starting` or `open`) and its parent share an edge of kind `lineage` (`PeerLinkBook.syncLineage`), rebuilt from `hub_children` at startup and on every `HubStartHost.changed`, none with the flag off. It has 60 messages (`PEER_LINEAGE_MESSAGE_BUDGET`), renewed by a message the user types in either chat, and no time window. `/unlink`, `STOP_SESSION` and an archive leave it; only the child leaving the open set removes it. It is not in `linksOf` (the banner); `list_agent_sessions` marks it `hub: 'parent' | 'child'`. `/link` with an open child on either side is refused (`CHILD_READ_ONLY_TEXT`), and an open child's agent may message only its parent. The send is card-less on a lineage edge in every mode but plan. A spent lineage budget refuses without a Not delivered row, since its Send would be a user message to an open child; the agent is told to report the message instead.
- **`delivery` on agent sends** (flag `hub_children`). With the flag on, `send_agent_message` takes `delivery: 'queue' | 'steer'` (default `queue`, also stored on its card). `peerDelivery` (`shared/turn-delivery.ts`) decides: an idle target gets an ordinary turn; mid-turn it steers only when asked, where `canSteer`, and not while the target's turn is compacting (`status.compacting` true, from the Claude and Codex adapters; Claude sends false when compaction ends) or being stopped (`INTERRUPT` while live); everything else queues through the `QueuedTurnLedger` under the received row's id (`verdict.id`), so an ACP target mid-turn is no longer refused. A send with no `delivery` (the flag off, `/send-to`, whose handler drops a client's `delivery`) behaves as before. Each delivered message logs `lineage`, `requested` and `delivery` on its `peer message delivered` line, which counts lineage traffic and steer fallbacks.
- **The link is checked again after the checkpoint await**, the one await between the charge and `sendTurn` (`peerDeliveryProblem`). The edge is compared by id (`PeerLinkBook.edgeId`), so an unlink there, or an unlink and relink, withdraws the send: the per-pair slot and the link charge are given back (`release` only refunds the edge that was charged), a checkpoint taken for a turn that will not happen is dropped, and the message is kept as a `link-removed` Not delivered row. A target that stopped or switched profile meanwhile is refused the same way.
- Sender-side provenance is a marker prefix, not a field: `[[sb:peer-sent]]` vs `[[sb:peer-sent-agent]]` (`parseRotationMarker` kinds `peer` / `peer-agent`), because a reload reads the stored string and has nothing else to tell the two apart.

## Codex app-server schema

`tests/fixtures/codex-app-server-schema.json` holds the app-server methods we send, answer or read, with every definition they reference, as generated by the installed CLI (`codexVersion` in the file; 0.162.1 on 2026-10-11). Regenerate it with `node scripts/codex-app-server-schema.mjs` (it runs `codex app-server generate-json-schema` with a throwaway `CODEX_HOME`; `--codex <path>` picks another binary). The method list is `USED` in that script: add a method there when the adapter starts to use it, or the tests fail with "not in the Codex schema fixture".

- `codex-adapter.test.ts` checks, after every test, everything the adapter wrote to the fake app-server (`tests/unit/helpers/codex-schema.ts`, strict: a key the schema does not declare fails). `codex-protocol-schema.test.ts` checks the fields `codex-adapter.ts`, `usage/codex-usage.ts` and `shared/codex-usage-parse.ts` read (the `*_READS` tables, kept by hand next to the code they mirror) and what the usage and reset probes send.
- Answers to server requests follow the request's method: `item/permissions/requestApproval` takes `{ permissions, scope }` (the requested profile, or `{}` to refuse, `scope: 'turn'`), not `{ decision }` (`codexApprovalResult`). Before 2026-10-11 the adapter sent `{ decision }`, which the schema rejects.
- **A permissions request grants only what its card listed** (`shared/codex-permission-request.ts`). `readCodexPermissionRequest` parses the profile once into the card's view (`request.opened.permissions`: one section per permission, every path; `detail` is the same list as plain text, never cut) and the granted profile, built from the same parse, so a field or path the card did not show is never granted. A field it does not know, more than 200 paths (`CODEX_PERMISSION_PATH_CAP`) or more than 32 KiB of listed text is refused before any card: a `tool.denied` names why and Codex gets `{ permissions: {}, scope: 'turn' }`. The desktop `ApprovalCard` and the Expo card list the sections in full; Android renders `detail` uncut. Full access still grants without a card, as for every other approval.
- `item/userInput/request` and `askUserQuestion` are not in 0.162.1; the adapter still answers them for older builds, and the helper skips them (`LEGACY_SERVER_REQUESTS`).
- 0.160.1 to 0.162.1 changed nothing we send or read: new optional `rootTurnId`/`parentTurnId`, a `partial_answer` message phase (we do not read `phase`), and `SkillMetadata.path` typed as a plain string.

## Provider instances (multi-account credentials)

- `provider_instances` table: `(id, agent_type, display_name, accent_color, auth_mode, env_encrypted BLOB, oauth_dir, config_json, enabled, created_at, updated_at)`. Multiple named instances per agent type (e.g. `codex-work` / `codex-personal`).
- `auth_mode`: `'env'` (safeStorage-encrypted env vars in `env_encrypted`) or `'oauth_dir'` (per-instance config dir set as `CLAUDE_CONFIG_DIR` / `CODEX_HOME`).
- IPC (`ProviderInstanceChannels`): `LIST` (secrets stripped), `UPSERT` (plaintext env in, encrypted at rest), `DELETE` (refuses last-of-kind), `TEST` (probes creds via `claude auth status` / `codex login status` / `opencode models`), `CREATE_OAUTH_DIR`.
- Registry resolves the instance at `startSession` (`resolveProviderInstance(agentType, instanceId)`), falling back requested → default → any enabled; applies the env overlay + oauth_dir at spawn.
- UI: `UnifiedProviderPicker` (drop-up: agent tabs → instance rail → model search) in the chat composer; `ProvidersTab` in Settings. Renderer cache in `provider-instance-store`.
- **Usage limits** (`ProviderInstanceChannels.USAGE` → `src/main/provider/usage/`): a per-row "Usage" button reads that instance's subscription quota. Claude via `GET /api/oauth/usage` with the instance's own keychain token; Codex via a short-lived `codex app-server` speaking `account/rateLimits/read`; OpenCode is not-applicable (own API keys). Normalised to `ProviderUsage` (`shared/provider-usage.ts`): `usedPercent` 0-100, `resetsAtMs` epoch ms. Traps:
  - Claude's per-model weekly limit is in `limits[]` as `kind: "weekly_scoped"`, **not** `seven_day_opus`/`seven_day_sonnet` (legacy, null). `is_active` marks which limit is *binding*, not whether it exists - never filter on it.
  - Codex's app-server wire is camelCase and `resetsAt` is unix **seconds**; the snake_case form belongs to `codex exec --json`. `account/read` needs an explicit `params`.
  - Keychain service = `Claude Code-credentials-<sha256(CLAUDE_CONFIG_DIR)[0..8]>`, derived from the **effective env value**, which is what makes lookup per-instance.
  - **Codex resets** (`shared/codex-reset.ts`, `usage/codex-reset.ts`): `rateLimitResetCredits` is `ProviderUsage.resetCredits`, not an overage row. `provider-instances:consume-reset` (admin-scoped) runs `account/rateLimitResetCredit/consume` on a fresh probe with the usage read's env, behind the same one-at-a-time Codex queue. Main mints the idempotency key on the click and keeps it per instance (`ResetKeyBook`) until a terminal outcome; `unknown` (timeout, dead server, unreadable reply) keeps it, so Try again cannot spend twice, and an edit keeps it too (only a delete drops it). Every outcome drops the cached reading and reads usage again. Never send consume in a test to anything but a fake app-server; never log the key.
  - Never reuse `runProbe` to read credentials: `security ... -w` prints the token on stdout, and `runProbe`'s callers surface stdout to the UI.
  - Tokens are never refreshed here - the CLI rotates and writes back, and racing it can log the user out. Expiry is checked locally.
  - Every `security` read of an item it has no lasting access to is a macOS password prompt, and Claude Code resets that access whenever it rewrites the item on a token refresh. So reads are shared per SERVICE, not per instance (`usage/keychain-read-cache.ts`: 45s window, concurrent reads joined, an item without a `claudeAiOauth` payload remembered for the process and never retried under the next account), only the user's Usage refresh or an instance edit reads past that, and nothing reads usage unasked: Settings prewarms the account list only, and Accounts reads once per visit.

## Skill exposure (shipped 2026-04-26)

`ProviderAdapter.listSkills?(threadId)` is the seam:
- **Claude adapter** captures `system/init.{slash_commands|commands}` and prefers live `query.supportedCommands()`. Cached on the active session.
- **Codex adapter** sends JSON-RPC `skills/list`, caches result. Older builds get a graceful empty cache (logged, not retried).
- **OpenCode** receives skills via `available_commands_update` ACP push events; the adapter caches the list and `listSkills()` returns it directly. (The earlier `opencode debug skill` shell-out was replaced when the ACP adapter was finalised.)
- IPC: `ProviderChannels.LIST_SKILLS` → `provider:list-skills` (preload `window.api.provider.listSkills(threadId)`).
- UI: `ChatInput` fetches on session start with retry-while-empty (handles late `system/init`); `mergeWithAgentSkills` keeps built-ins first, name-collisions resolve in favor of built-ins so `/clear` always means "clear chat" not whatever a skill named `clear` does. `SlashCommandMenu` renders source-grouped sections + argument-hint suffix. Agent-source selections insert `/<name> ` into the textarea (no special wire path) - the SDK / CLI parses leading slash from the prompt itself.

Pure parsers exported and unit-tested: `parseClaudeSlashCommands` (claude-adapter), `parseCodexSkills` (codex-adapter), `mergeWithAgentSkills` + `skillsToSlashCommands` (slash-commands.ts).

## OpenCode adapter

OpenCode ACP adapter (2026-04-28, only OpenCode adapter - legacy `opencode run --format json` shell-out retired 2026-05-02): speaks the Agent Client Protocol over a long-lived `opencode acp` child. Dynamic model list, shell-env probing for API keys, settings-DB key injection, placeholder + heartbeat + 3-min timeout (free-tier-aware error message) for cold-boot UX. Skill discovery via `available_commands_update` ACP push events. Helper: `adapters/opencode/env.ts` for shared env-probing.

- **Generic ACP agents** (2026-10-08). `adapters/acp/acp-adapter.ts` is the ACP adapter for every ACP agent; an `AcpLaunchConfig` (`adapters/acp/launch-config.ts`) holds what differs: binary lookup, start args, env, preflight, a config reader (`prepareSession`: spawn env, which permission requests are our own MCP tools, approval-card tool names), mode mapping (`fixed` build/plan for OpenCode, `advertised` for the rest: plan goes to an advertised `plan` mode, or is enforced by the permission policy alone when there is none; every other runtime mode goes back to the mode the session started in), model labels and variants, expected capabilities (a warning only) and a first-prompt hook. `OpencodeAcpAdapter` is `AcpAdapter` with `OPENCODE_ACP_LAUNCH`; its tests mock `opencode/env`, `opencode/version`, `child_process` and the SDK by path, so keep those import paths. `adapters/acp/agents.ts` holds Gemini CLI (`gemini --acp`; `--experimental-acp` is the deprecated spelling), Mistral Vibe (`vibe-acp`), Cline (`cline --acp`) and Copilot (`copilot --acp`), each verified against docs only, never run here. Models come from `session/new` `models` or a `category: model` config option (set with `session/set_config_option`). A missing CLI is not offered (`IS_AVAILABLE` per kind; `renderer/services/acp-agent-availability.ts` filters the picker tabs and Settings > Accounts, keeping a chat's own agent and agents with a user-made account). Settings Test only looks for the binary: never start one of these agents against an account to test it. Every ACP agent is blocked on remote machines, never steers (`speaksAcp` in `shared/acp-agents.ts`), cannot keep a thread across a profile switch, forks by transcript handoff (native fork stays OpenCode only), and gets no auto-allow for Switchboard MCP tools (their tool naming is undocumented). Phones show and continue their chats but do not offer them yet (staged: `mobile_generic_acp_agents`, `native_generic_acp_agents`). Adding an agent: an id in `GENERIC_ACP_AGENTS` with labels, a spec in `agents.ts`, a case in `tests/unit/acp-launch-configs.test.ts`, and the Android `ProviderKind` / `AcpAgents` entries.
- **Local commands and Add agent** (2026-10-11). `acp-command` is a generic ACP agent whose launch comes from each account: `config_json.launch` (`shared/acp-command.ts`: command, args, cwd) read by `ACP_COMMAND_LAUNCH` in `adapters/acp/agents.ts` through the optional `instanceId` on `AcpLaunchConfig.findBinary` / `args` / `spawnCwd`. It has no seeded default row, is never probed by `IS_AVAILABLE` (offered only through its accounts), and UPSERT refuses one without a valid launch. Creating one, or any UPSERT carrying `configJson`, and `provider-instances:test-draft` (the Test probe for an unsaved account) need the `terminal` scope (`isAccountWriteAllowed` in `shared/device-auth.ts`), since both name a program the backend runs. `config_json.startMode` is the account tier of `resolveSessionDefaults`: the Add agent dialog (`renderer/components/settings/AddAgentDialog.tsx`) stores `plan` for every agent not tested with Switchboard, and it beats the machine default but never a mode the user or the conversation chose. The account is looked up by the chosen id or `<kind>-default`, so a local command chat started with no account named falls through to the machine default. Registry search there is staged behind `ACP_REGISTRY_SEARCH_ENABLED` with a stub source (`acp-registry-source.ts`); do not invent an index URL.
- **ACP SDK 1.x** (`@agentclientprotocol/sdk` ^1.8, from 0.21 on 2026-10-11). The SDK dropped the unstable model selectors in 0.24: no `ModelInfo` type, no `models` field on `session/new` or `session/resume` replies, no `unstable_setSessionModel`. Replies are not validated, so an agent's `models` still arrives; `legacyModelCatalog` (`acp/session-config.ts`) reads it, and `session/set_model` goes out through `connection.request`. OpenCode 1.18.33 itself now sends `configOptions` (`model`, `mode`) and no `models` or `modes`, so its model changes take the config-option path; `session/set_model` and `session/set_mode` still answer. `ClientSideConnection` and `AgentSideConnection` (the tests' fake agent) are deprecated in 1.x in favour of `client({ name }).connectWith(...)` / `agent({ name })`, and still work; move to them before the SDK removes them.
- **OpenCode 1.x by default, 2.x behind `opencode_v2_acp`** (2026-09-29, flag 2026-10-15). OpenCode 2.x is the same `opencode` binary (curl installs it to `~/.opencode/bin/opencode`, v1's path too; npm `@opencode/cli`; brew `opencode-v2`, which conflicts with `opencode`) and it breaks us: `acp` takes no options, so our `acp --cwd <dir>` is rejected before ACP starts; `session/set_model` is gone (the model is a `session/set_config_option` with `configId: "model"`, `"effort"` for the variant) and `session/new` returns `configOptions` instead of `models`; and `opencode models` attaches to a shared background service spawned with its first caller's env, so an instance's API keys may not apply. `adapters/opencode/version.ts` reads `opencode --version` once per binary (keyed by path, mtime and size) and `assertSupportedOpencode` throws `OpencodeUnsupportedVersionError` for major >= 2 while `opencode_v2_acp` is off (major >= 3 always) before the adapter start, the native-fork runner, the catalog probe and the Settings Test spawn anything. `--version` runs in the spawn's cwd, and the cache is keyed by cwd and by `opencodeEnvFingerprint` (a hash of PATH, HOME, `OPENCODE_*`, `XDG_*` and version-manager keys, never logged), for shims and wrappers that pick an install per directory or env. A native fork that is refused falls back to the handoff with the refusal as its warning (`native-fork-unsupported-version`). When it fails or is unparseable, `opencodeV2InstallSignal` judges the files without running anything: an `opencode2` shim beside the binary (v2's curl installer and `@opencode/cli`'s second npm bin; v1 has neither) or a real path in `@opencode/cli` or brew's `opencode-v2` Cellar means 2.x. With no version and no signal the binary is let through (a 1.x must not be locked out), and that is the known hole: a renamed or hand-copied 2.x that cannot print its version would run and could migrate `opencode.db` one way. Unparseable output is logged as a byte count only. The v2 path is behind the staged flag `opencode_v2_acp` (`OPENCODE_V2_ACP_ENABLED` in `version.ts`, false; `SB_OPENCODE_V2_ACP=1` in Switchboard's own env turns it on). With it on, `assertSupportedOpencode` returns the generation (1 or 2; 3.x and later still refused; an unversioned install with a v2 signal is 2) and `opencode/cli-args.ts` (apart from `version.ts`, so tests that mock the gate still get real args) builds the command lines from it: `acp` with no `--cwd` (the spawn cwd is the folder) for the adapter and the native-fork runner, `models --standalone` for the catalog probe and the Settings Test. The adapter's `preflight` returns those args and `effortConfigId: 'effort'` for 2.x (`AcpPreflight`). The model is always a config option once `session/new` returns one; while the session has an effort option (named by the preflight, or the first `thought_level` option a `modelVariants` agent reports), `applyModel` splits `provider/model/variant` with `splitConfigModelId` (an id the catalog lists whole is never cut), sets the model, then the effort (`default` is the base and is set back on a pick with no variant, since 2.x keeps the level across a reselect), and emits `model.variants` from the effort option (empty for a model with none, where 2.x drops the option and refuses an effort). Config-option model changes run one at a time on `active.modelChange`, and a pick a newer one replaced is skipped, so the agent never ends on an older pick. A 1.x session reports no effort option, so its ids stay whole and it gets no new event. `isChildSessionText` drops a subagent's text chunks, which 2.x streams into the parent session with `_meta["opencode/child-session"]`. Live on 2.0.29 (private HOME and XDG dirs, free models, 2026-10-15): MCP tools run inside a code-mode `execute` tool, so a permission request names `execute` with the code as rawInput, never `switchboard_*`; the injected `switchboard_*` allow rules still apply inside it; the question tool reaches ACP only as a failed tool call; background subagents and background shells both stream over ACP. Before the flag goes on: check a signed-in provider, the approval card for an `execute` call, and place a subagent's tool calls under its row. Also note v2 migrates `opencode.db` forward in place and moves `auth.json` credentials into it, so a downgrade is not guaranteed clean.
