# Switchboard MCP server

Detail for this part of the code. The root `AGENTS.md` holds the rules that apply everywhere (shipping checklist, cross-surface policy, logging, writing style); they apply here too.

## Switchboard MCP server (`src/main/mcp/`, agent tools for supported providers)

One MCP server per backend process gives Claude, Codex and OpenCode the same tools, and is the ONLY gate for them. Verified live against the CLIs (2026-09-27): Claude routes an MCP tool through `canUseTool` and asks nothing else; Codex (sandbox) confirms a non-read-only tool with a yes/no `mcpServer/elicitation/request`, never in full access; OpenCode never asks for an MCP tool unless the user's own config says so, and its plan mode is the model obeying, not enforcement. So the server enforces plan mode, the approval card, the budget and the link check itself.

- **Transport.** `stdio-bridge.ts` holds a dependency-free CommonJS bridge that `ensureStdioBridge` writes to `<userData>/mcp/switchboard-mcp.cjs`; each agent spawns it (`process.execPath` with `ELECTRON_RUN_AS_NODE=1`, so the Electron binary or the headless server's node) as its `switchboard` MCP server. The bridge dials the backend's `127.0.0.1` listener (`switchboard-mcp-server.ts`), sends `{ switchboardMcpAuth: <token> }` first, then pipes. The token is read from a 0600 file under `<userData>/mcp/tokens/` named by `SWITCHBOARD_MCP_TOKEN_FILE`, never passed as a value: Codex's `-c` and Claude's `--mcp-config` put the server's env on a command line any local user can read with `ps`. Kept as source rather than a second bundle so a provisioned VM needs nothing extra. The protocol (initialize, ping, tools/list, tools/call, notifications/cancelled) is hand-rolled in `mcp-session.ts`; `@modelcontextprotocol/sdk` is only transitive here.
- **Token = identity.** `ProviderRegistry.openSwitchboardMcp` mints one per session start (`mcp-tokens.ts`, sha256 in memory), and the tools are built for THAT thread; `STOP_SESSION` revokes it, deletes its file and drops live connections. The mode the gate reads is the adapter's own (`ProviderAdapter.runtimeModeOf`), because a queued message's mode applies only when it starts. Links and the budget key on `resolveRootThreadId`. A registry built with injected adapters (tests) gets no server unless one is passed as the 5th constructor argument.
- **Registration** (`agent-registration.ts`, pure): Claude via the SDK's `mcpServers`; Codex via `-c mcp_servers.switchboard.{command,args,env,tool_timeout_sec}` on its per-chat `app-server` (raised to 180s: no call waits on a card any more, but a full-access create makes several host calls with no card, and Codex gives up after 60s by default); OpenCode via ACP `session/new` `mcpServers`. User MCP servers keep loading from their own config.
- **No second prompt, only when OUR server was registered**: Claude's `canUseTool` allows `mcp__switchboard__*`, Codex's confirm for `serverName: 'switchboard'` is accepted, OpenCode's permission for `switchboard_*` is allowed. Without a registered server those names get the ordinary policy, so a user server that calls itself `switchboard` is not trusted.
- **Tools.** Reads, no card: `get_pr_status`, `list_pr_conversations`, `get_pr_diff` (pages of at most 60 KiB, `mcp/pr-diff-page.ts`). Writes, one card each: `reply_to_conversation` (text, optional `resolve`), `resolve_conversation`, `rerun_check` (GitHub Actions only), `comment_on_line` (one inline comment, the line must be in the fresh diff), `draft_review` (summary plus up to 30 comments, 40 KiB; one write against the budget). Never merge. A verdict is never the agent's: `draft_review` has no verdict argument (one sent is refused, `shared/agent-pr-review.ts`), the card preselects none and offers only what `reviewEventsFor` allows (an author or a closed PR gets Comment only), and an answer without a verdict posts nothing. `create_pull_request` (one card: editable title and description, the repository and "source -> target"; rules in `shared/agent-pr-create.ts`) is the one write that needs no linked PR: it opens one on the repository the chat's `project_path` points at (any other `repository` is refused), from the session cwd's current branch (`pull-requests/branch-check.ts`, which also refuses a branch `git ls-remote` does not find on that repository's remote) into the host's default branch unless given. For a project folder that holds several repositories, optional `repoPath` (relative to the project folder or absolute) names one: `resolveRepoDir` (`pull-requests/project-repos.ts`) realpaths both sides and refuses anything not inside the folder (the folder itself allowed, so no `..` or symlink escape) or not a git work tree. A folder outside (a worktree in /tmp) is accepted only when it is a linked worktree of a repository whose main checkout is inside: its `git rev-parse --git-common-dir`, realpathed, must be a `.git` folder inside the project folder, and that main checkout's `git worktree list` must hold it, so a hand-made `.git` file does not count. `mainRelPath` names that main checkout; in a project that is a repository a `repoPath` must be its own checkout or a worktree of it (`mainRelPath` '.'). Its remote is the repository (a `repository` given too must match it exactly, `repoPathRepositoryProblem`) and must be one the project covers (see Chat ↔ PR links), and the branch checks run with it as the cwd. Without `repoPath`, a parent folder plus `repository` picks the ONE child work tree whose remote matches (`findChildRepo`), refusing zero or several with the candidates listed; the chat's own checkout wins when it is that child or a worktree of it (it is the source branch then, and it settles several matches), and with neither argument the chat's checkout alone picks its child. A refusal that a new checkout could change (no children, no match, several) is tried once more against a fresh scan. The card shows that path (`create.localPath`), desktop and plain-text detail only: it is not in `hostWritePreview`, so the phone digest and its pinned vectors are unchanged (the repository is already in `target`). An OPEN PR for the source branch is linked and returned instead, before the card and again in `PullRequestService.createPullRequest`. Optional `reviewers` (at most 10 logins, display names or emails; GitHub teams as `team:<slug>`) are matched before the card against `PullRequestService.reviewerPool` (the Reviewers card's candidates plus the signed-in user) by `shared/agent-pr-reviewers.ts`: exact, case and a leading `@` aside, on id, login, display name, a listed email or a team slug; without an exact match the ONE person whose id, login, display name or team slug holds the name (or is held by it) is taken, and the card shows who; a shared word or an email domain never picks anyone. A name matching several people, several close ones or nobody, or the signed-in user, is refused with the candidates listed. The card lists them (`create.reviewers`), removable on the desktop; the approval sends the kept ids. Bitbucket sends them in the same POST (`reviewers: [{uuid}]`); GitHub creates the PR and then posts `requested_reviewers`, and when that second call fails the PR stays (`OpenedPr.reviewerFailure`): the agent gets the URL and the reviewers that failed, and the create is never re-sent. `draft` is GitHub only and refused on Bitbucket. After a create it links the PR to the ROOT conversation (source `created`, which relinks a tombstone) and emits `pull-requests:links-changed` with `created: true`, which marks the Reviews list stale (`review-store.markStale`). An `offline`/`unknown` failure is uncertain: it looks for the PR once, and otherwise tells the agent not to create again. The MCP server's instructions tell agents to use it instead of `gh pr create`, bbpr or a host API. Link tools, no card (`mcp/pr-link-tools.ts`: a link changes only what these tools may act on, nothing on a host): `link_pull_request` (a URL, or `repository` + `number`; the `pull-requests:link` repository rule; source `agent`) and `unlink_pull_request` (tombstones, like Reviews' Unlink), both denied in plan mode through `decidePermission`, and `list_thread_pull_requests` (each link's source and last known state, plus the chat's last automatic linking failure), which runs unasked. Plus the two session tools. Every other tool acts only on PRs linked to the calling chat (`pickLinkedPr`), through the same `PullRequestService` as the human writes (`setAgentPullRequestAccess`, set in `registerPullRequestHandlers`), so its re-reads and validation apply.
- **Modes.** Plan denies a host write without a card. Full access STILL shows the card: posting as the user on GitHub or Bitbucket is not a local edit (`hostWriteGate`). Sandbox, accept-edits and auto show it. The one exception is `create_pull_request` (`createPullRequestGate`): full access opens the PR without a card, because the user asked for it, it merges nothing and closing it undoes it. It still counts against the budget and still carries the via-Switchboard marker.
- **The card does not hold the turn** (`mcp/agent-approvals.ts`, rules in `shared/agent-approval-cards.ts`). It is a `request.opened` with a `hostWrite` payload (`shared/agent-host-writes.ts`) and a plain-text `detail` for clients that do not render it; ids start `sbmcp_` and `RESPOND_TO_REQUEST` routes them to the broker, with an optional 4th argument `{ text, resolve, quiet, ... }`. The tool returns AT ONCE, not as an error: "Queued for the user's approval (card <id>) ... Do not send it again." The card is stored with the write it would run as data (`plan`: `PrWritePlan` in `pr-tools.ts`, `PeerSendPlan` in `peer-mcp-tools.ts`) in `agent_approval_cards` (`db/agent-approval-cards.ts`, keyed by the ROOT conversation), so it waits until the user answers or the chat ends and survives the turn ending, a profile switch or relocation (the internal `stopSession` leaves it) and a backend restart (the broker loads the table, parsing each row on its own: a row it cannot read is deleted and its chat gets a failed result row, so one bad row never drops the rest; `getPendingRequests` serves the broker's cards, not the registry's per-turn record, so a `status: error|stopped` cannot drop them). It closes exactly once (`ApprovalCardBook.take`): approved, approved quietly, denied, dismissed (a quiet deny), withdrawn by the agent (`withdraw_approval`, its own chat's cards only), or closed by the user's `STOP_SESSION` or an archive (`closeAgentCards`). The one time limit is a safety cap: a card unanswered for 7 days (`AGENT_CARD_MAX_AGE_MS`) closes unsent (`expireOld`, run at startup and whenever a card is opened, recovered or answered; outcome `expired`, the agent is not woken), and every card says so (`AGENT_CARD_LIFETIME_TEXT`: appended to the plain-text detail, and a line on the desktop, Expo and Android host-write cards). `notifications/cancelled` or a dropped connection no longer touch a card: the agent has already moved on. Only an approval runs the write (`runPrWritePlan` / `runPeerSendPlan`), with every check after the card that ran before: plan mode, the PR link, the project's repository, the edited text, a phone's `shown`, and for a peer send the whole `deliverPeerMessage` path (link rules, budget, refund, Not delivered row, the re-check after the checkpoint). `reply_to_conversation` with `resolve` stays ONE card that does both. The text the user leaves in the card is what is posted, ending with a `via Switchboard` line (`withViaMarker`). Then `reportAgentCard` stores a `[[sb:approval-result]]` system row under the root id (`ApprovalResultRow`, desktop `ApprovalResultRow.tsx`, both phones show `approval.result` and the stored row as a notice) and, unless quiet, delivers the result to the agent as a turn of its own (`approvalResultTurn`): a new turn when idle, `delivery: 'queue'` behind a running turn (the `QueuedTurnLedger` path), or held in `agent_approval_results` and sent when the chat's session next starts (a result answered during a profile switch or relocation is held too, and `flushHeldApprovalResults` sends it once that move commits or rolls back). That turn is wrapped in `<switchboard-approval-result>`, says it is from Switchboard and carries no authority, and every surface's synthetic split drops it (`synthetic-message.ts`, Android `SyntheticUserMessage.kt`), so the row is what the user reads. **It is not a user turn**: `sendApprovalResultTurn` sets no `turnDepth`, renews no link and clears no plan, so a result can neither restart a peer chain nor spend or refill a link's budget (`agent-approval-results-registry.test.ts`). A call still sends `notifications/progress` every 10s when the client gave a progress token, now only for slow host calls a full-access create makes without a card: OpenCode's MCP call timeout is 30s and not settable over ACP.
- **Phones** approve a host write card as drafted: a device with the `chat` scope (a phone) may approve, because it can already send the agent full-access turns, which is the larger power. The Reviews write channels (`PullRequestWriteChannels`: merge, the user's own comments and reviews) stay `admin`-scoped, except the subset a desktop-granted `pr-write` phone may call (see `src/main/pull-requests/AGENTS.md`, Phone writes). The backend advertises `agent_host_write_phone_approval_v1` (`shared/host-write-phone.ts`); a phone without it offers Deny only, since an older backend refuses the approval. The phone card (`phoneHostWriteButtons`, ported to Android as `HostWriteCards.kt`) shows everything the approval posts, uncapped, from the card payload (`hostWritePreview`: title, description, reply, summary, every review comment under its `path:line`), never the capped plain-text detail; a long draft starts collapsed and no button approves until it is opened, and a payload the phone cannot show in full (null preview) is Deny only. A create's reviewers are a `Reviewers` section of that preview (one `Display (login)` line each), so the digest covers them and a phone approves all of them. It has an action-named button, and for `draft_review` one button per offered verdict with none primary. It never edits: the registry passes only `resolve` and `verdict` (`approvalChoiceOnly`) from a device without the `admin` scope, so a phone's approval posts the draft it showed. It must also carry `shown`, the `hostWriteShownDigest(requestId, card)` of the draft it rendered in full: FNV-1a 64 over the request id, the card's `target` (host, repository, PR number; for a create, the source and target branches), the action and exactly what `hostWritePreview` shows, so the same text on another card or PR does not match. Ported as `HostWriteCards.shownDigest`; two cross-implementation vectors are pinned in both test suites. The broker recomputes it from its card and refuses a missing or different one ("Update the Switchboard app..."), so a build that showed the capped detail cannot approve. The desktop needs none. Deny never needs it. **Editing an agent draft on the phone before approving is deferred** (the user, 2026-09-29: not a priority). The design when it comes: the phone sends its edited text (and kept reviewers), `approvalChoiceOnly` lets those fields through for a `chat` device, and `shown` is computed over the edited text rather than the card's, so the broker can check the phone approved exactly what it will post. The broker refuses a review approved without a verdict the card offered (`hostWriteApprovalProblem`) and keeps it open, and logs which device approved (`describeRequestClient`). Every other guard (the re-checks after the card, plan mode, budget, link rule) is unchanged. The peer-send card stays answerable from a phone, as before. No client expires a card on its own (only the backend's 7-day cap closes one), so an hours-old card recovered through `GET_PENDING_REQUESTS` renders and answers like a new one. On a backend advertising `agent_async_approval_v1` (`AGENT_ASYNC_APPROVAL_CAPABILITY`) both phones offer "Don't wake the agent" on a server card (`offersQuiet` / `quietly` in `apps/mobile/src/lib/approval-actions.ts`, `ThreadInteractionPolicy` on Android): it adds `quiet: true` to the same response (Approve becomes "... quietly", Deny becomes Dismiss), and `approvalChoiceOnly` keeps it for a `chat` device. An older phone simply never sends it.
- **Guards**: 10 writes per chat per 10 min, counted when a write reaches its card (the cap is checked first, so a refused card costs nothing); at most 20 OPEN cards per chat (`AGENT_OPEN_CARD_CAP`), past which a new ask is refused with `isError` and told to wait or withdraw one; reply text capped at 8,000 chars; every refusal is tool output with `isError`.
- **Known limit: a write in flight is not atomic with its checks.** Every write re-checks the link and the mode after the card and again before a second write (reply, then resolve), and a peer send re-checks the mode after its card. An unlink, cancel or stop that arrives after the last check cannot stop a host call that has already started. An uncertain result tells the agent not to post again; there is no host-side dedupe key. Since a card can now be answered hours later, the PR the card shows may have moved on (new commits, a resolved thread): the host call itself refuses a stale target where it can (the service re-reads before a write), but the card's quoted text and diff excerpt are as of when it opened. A result turn the adapter refuses is held and retried at the next session start, not retried in place.
- **Child chats** (flag `hub_children`, off; `hub-tools.ts`, runner `main/hub/hub-start.ts`). With the flag on, a chat that is not an open child gets `start_children` and `list_children` and the `HUB_INSTRUCTIONS` paragraph (`SwitchboardMcpServer.open`'s 3rd argument). **Machines** (flag `hub_remote_children` too, off): such a chat on the desktop's own backend (not under `SWITCHBOARD_REMOTE`, and only once `ipc/machines.ts` handed the registry its `RemoteHubClients` through `setRemoteHubClients`) also gets `list_machines` (read only, no card) and the `LIST_MACHINES_INSTRUCTIONS` line after the hub paragraph; with the flag off the tool and the line are absent and the paragraph is unchanged. It answers one block per machine, `local` first (described in process by `describeThisMachine`, the builder behind `hub-remote:describe`), then every saved machine from the client's cache: id, the user's name for it, transport, status (`error` while the hub client refuses the machine), the description's age, OS and arch, agents with their accounts and models, projects whose remote matches the chat project's (`remoteUrlKey` in `shared/hub-remote.ts`: host and path, lower case, so https, ssh and scp forms match), free disk, open children and free run slots, plus a line when `flagOn` is false or the backend needs an update. It never writes a host name, ssh alias, cloud project, zone or user: `formatHubMachineList` reads only `HubMachineEntry`. `RemoteHubClients` (`main/hub/remote-hub-clients.ts`) opens one `WsTransport` per connected machine on `ConnectionManager` status (`?auth=frame`, the backend token with `scopes: ['hub']`), refuses an `authed` other than exactly `['hub']` or a `ready` without `hub_remote_child_v1` ("update the backend on <name>"), closes on any other status and on delete or quit, and refuses a call to a machine that is not connected at once; a call times out after 20 s (`hub.remote-call` perf line). It reads `hub-remote:describe` on each connect and at most every 60 s from `list_machines`; an offline machine keeps its last answer with its age, and a failed read stores nothing. Nothing opens while the flag is off. **`machine` on a task** (flag `hub_remote_children`): `start_children` documents `machine` (an id from `list_machines`; `account` is then an account id on that machine) only where `list_machines` is offered. `parseHubTasks` checks type and length (64); `local` or absent is the parent's own machine. With the flag off, or on a parent under `SWITCHBOARD_REMOTE`, a task naming another machine is refused. `HubStarter.propose` checks each such task against the hub client's cache (`HubStartHost.machineEntries`, the pure `planRemoteTask` in `shared/hub-remote.ts`; first problem wins, naming the task): known machine, connected, no client problem, a description at most 90 s old, `flagOn` there, a login and the named account and model for the agent, `location: 'worktree'`, a parent project with a git remote; a description project whose `remoteUrlKey` matches gives the path, else a clone into `~/projects/<repo>` is planned (that machine clones it at start). The base ref resolves to a SHA in the parent checkout that `git branch -r --contains` finds on a remote branch (the parent's upstream first, `pickFetchBranch`; Switchboard does not push), and each machine's disk is checked against its `freeDiskBytes` and its `minFreeGiB` (tracked bytes of each base, plus one checkout for a clone). The stored `PlannedChild` carries `machine`, `remoteProjectPath`, `clonePlanned` and `fetch`; a plan stored before has none and is local. **A batch with any remote child always opens the card**, in every mode (`hubNeedsCard(mode, hasRemote)`); its rows carry `machine` and `clone`, the view `remoteDisk`, and `hubBatchDetail` names the machine per row. Approval re-reads the machines (`remoteApprovalProblem`: connected, no client problem, `canStart`, the account still listed). **Start on the child machine** (`hub-remote:start-child`, capability `hub_remote_start_v1`; an entry's `canStart` is false without it, and `planRemoteTask` and the approval then say "update the backend on <name>"): `HubStarter.runBatch` sends each remote child to its machine (`HubStartHost.startRemoteChild` -> `RemoteHubClients.invoke`), at most 2 at once per machine, next to the local children. The request (`HubRemoteStartRequest`, `parseHubRemoteStartRequest` checks every field) carries the desktop's `hub.installId` (minted once, `hubInstallId`), the parent and child ids (the child keeps its id there), title, brief, agent, account, model, the granted mode, `baseSha`, `fetch.remoteBranch` (the branch name on that remote, without the desktop's remote name), `repoUrl` (that remote's URL through `hubRepoUrl`: no password, no http user part, no query; an ssh login stays; a local path is refused), `remoteProjectPath`, `clonePlanned`, the dependency setting and the task's `branch` (`HUB_BRANCH_RE`, the local rule; null seeds from the title). The URL and the setting are recorded in the `PlannedChild` at propose (`repo`, read by `remoteOfBranch` in the parent's own checkout, and `depsSetting`, which the card shows on remote rows as `deps`); a plan stored before them reads the URL in the project folder at start and sends the live setting. `fetch.remoteBranch` must pass `isBranchName` (`git check-ref-format --branch` rules: no component starts with `.` or ends with `.lock`, not `@` or `HEAD`). On the child machine `HubStarter.startRemote` refuses with `hub_remote_children` off there, refuses a parent id or child id that names a chat there (or a rotated id of one) or a parent id that is a hub parent there (no stub is claimed), answers a child id it has with that child's state and starts nothing (another hub's id is refused), refuses over `hub.remoteChildrenPerMachine` (default 4, clamped 1 to 12; open and starting children under parent stubs), refuses an account it does not have, lowers the mode to `hub.remoteMaxMode` (default `auto`, any runtime mode; `grantedMode` order) and answers the mode used, claims a **parent stub** (`hub_parents.remote_hub` = the desktop's install id; additive column) and inserts the child row before its first await. Then it expands `~`, clones `repoUrl` with this machine's git when the folder is missing and a clone was planned (`cloneProjectAndWait` in `ipc/project-clone.ts`: the same URL checks, journal and cleanup; one checkout step at a time per folder, so two children that plan the same clone clone it once), refuses a missing folder without a planned clone and a folder with no configured remote whose `remoteUrlKey` matches, fetches `refs/heads/<branch>` from that configured remote into a scratch ref and checks `baseSha` is in it (`HubStartIo.fetchBase`), plans the dependencies with the request's setting, checks this machine's disk against its own `hub.minFreeGiB`, and runs `prepareChild`, the same path a local approval uses (worktree at `baseSha`, `managed-in-repo`, deps, run slot `runningPerInstance`, session, brief). It answers `{ ok, phase, mode }` once the child is open or failed, or `starting` after 12 s (`HUB_REMOTE_START_WAIT_MS`); an error names paths under that machine's home as `~`, so its user name stays there. A refusal names the machine on the desktop (`hubRemoteStartFailureText`), an older backend's `no handler` (`isNoHandlerError`) reads "update the backend on <name>.", and each failure is `failed_start` with a `failed` wake for that child only; a throw in one child's start fails that child and its lane goes on. A call with no answer (a timeout, a closed client) is not a failure: the row stays `starting`. **Reconcile** (`HubStarter.reconcileRemote`): every desktop row in `starting` with a `machine_id` sends the same request again, rebuilt from the stored plan (`storedChild`), since the request is idempotent by child id; it runs at launch (`setRemoteHubClients`), on each connect of that machine (`RemoteHubClients.setMachineListener`, one listener, the current registry) and, after a `starting` answer or no answer, every 15 s (`HUB_REMOTE_FOLLOW_UP_MS`) up to 8 times in a row; nothing is sent with `hub_remote_children` off, and `stopAll` clears the timers (`HubStarter.dispose`). An answer applies only while the row is still `starting`; a machine that is not connected waits for its connect (`HubStartHost.remoteMachineState`), and a removed machine (`RemoteHubClients.remove`, or `gone` at reconcile) fails its starting rows with "<name> was removed before it answered the start.". On success the desktop row (`hub_children.machine_id`, additive, null = this machine) takes the phase and the mode used, never above the mode it granted. Every `fail` pumps the run-slot waiters, so a remote child leaving `starting` lets a waiting local child go. A stub parent is never sent a turn and no session runs for it there. **Outbox** (capability `hub_remote_outbox_v1`, `main/hub/hub-outbox.ts` on the child machine, `main/hub/hub-remote-outbox.ts` on the desktop): everything a child sends its stub parent is a `hub_outbox` row (`id`, `child_id`, `parent_id` = the stub id, `kind` `wake` or `message`, `payload_json`, `created_at`, `acked_at`; additive), never a `hub_wakes` row there. `insertHubWake` sends every wake of a stub parent there (report, failed, blocked, stopped, limited, resumed, restart: the summary cut at 16 KiB, the pointer's `at` and `toolCallId` (left out over 200 characters, here and in the migration) without the transcript path, and the child's phase then), and the migration moves older stub wakes there once (`ho_<wake id>`); `lastHubWakes` and `lastHubWakeOf` read the outbox too, so the reaper and a repeated start still see the last wake. A child's agent send to its stub parent (listed by `list_agent_sessions` as `Parent chat (on another machine)`, `hub: 'parent'`, no provider) is a `message` row (`ProviderRegistry.relayToParentStub`: 16 KiB cap, at most 60 unacked per child, `delivery` kept, no budget charged there; the tool says it waits for the other machine); any other target keeps the ordinary rules. Each insert emits `hub-remote:outbox` (no payload) through the host, which sends it only to sessions holding `hub` or `admin`. `hub-remote:outbox-pull { v: 1, desktopInstallId, after?, limit? }` (100 by default, 500 at most) answers unacked items of stubs whose `remote_hub` is that id, by (created_at, id), after `after`, with `cursor` (the last row read after a full page, else null); a row that no longer parses is deleted there with a log line, so it never stalls paging or warns again. The caller names the install id and is not bound to it: the `hub` scope is the trust boundary (one token per machine); `hub-remote:outbox-ack { v: 1, desktopInstallId, ids }` (500 at most) marks only that desktop's items, idempotent; acked rows are deleted after 7 days (at start and on ack). Both answer with the flag off, so running work can finish; every field is checked and nothing builds SQL from input. Wake and outbox ids sort by creation within a millisecond (`newHubRowId`). The desktop (`HubRemoteOutbox`, set up in `setRemoteHubClients`, nothing with the flag off, only from a backend that advertises the capability, logged once otherwise) pulls on the event, on each connect (with `reconcileRemote`), at launch for machines already connected, and when the client is ready again after its socket reconnected or on a resume gap (`RemoteHubClients.onResync`), and on each connected machine (with `reconcileRemote`) when `hub_remote_children` turns on (`RemoteHubClients.enabledChanged`); one pull at a time per machine and one more for a request during it; pages after each answer's `cursor` (from an older machine without it, until a short page); a pull that throws is tried again every 60 s up to 5 times in a row (`hub.outbox-pull` perf line: pages, items, oldest age, retries, outcome). Each item is imported once per (machine, item id) in `hub_remote_imports` and acked only after that committed, so a lost ack re-pulls it and nothing is imported twice; import records are never pruned, since the child machine keeps an unacked item with no age limit. An item is trusted only for its own machine: its child must be a desktop row with that `machine_id` and that parent and not settled, else it is recorded `dropped` with the reason and acked. A wake becomes a desktop `hub_wakes` row (`machine_id`, additive) through `HubWakeScheduler.record` in the import's transaction, so the scheduler runs unchanged; a failed or stopped wake written at a failed start there ends a starting or open row `failed_start` (`HubStarter.remoteChildFailedStart`, which pumps the slot waiters). A message is claimed (`delivering`) and then delivered by `deliverPeerMessage` from the child to its parent along the lineage edge (`deliverRemoteChildMessage`: open child of that machine, live edge, the edge charged first, the parent's own framing naming the child, no row or event for the child's chat here); a refusal (budget, a stopped parent) is recorded `refused` and never tried again; a parent that is not running or is switching profiles is pulled again every 60 s up to 5 times before that (one try per 60 s, however many pulls ran), and messages past the per-pair rate (a backlog after the machine was away) wait for the next pull without using up those tries. Three hooks mask the exact, base64 and base64url forms, and the value with any of its characters escaped (a percent escape in any case, so every URL and form encoder, `+` for a space; a backslash or JSON `\uXXXX` escape; the shell's `'\''` and `'"'"'`), as `[secret NAME]`: `ProviderRegistry.publish` (every runtime event, through `RuntimeEventRedaction`, which holds back the tail of a streamed message that could still grow into a match (`holdFrom`), one carry per message id, stream kind and parent tool call, at most 16 per thread, until a snapshot replaces the message or the turn stops; changed-file cards go through its `mask` and get `noRevert: 'unknown'`), `db/secret-mask.ts` (`maskStoredText`, used by every writer of message text, so every row and the FTS index; a fork's scope adds its fork ancestors' secrets), and `conversations/history.ts` (every history read; the memo keeps the unmasked read). A hit posts one `SECRET_MASKED_TEXT` system row per turn (a changed-file hit names the file). The main logger masks every line it writes (file and console) with every live value (`redactAnyText`), adapters mask a payload before they truncate it, and Codex, Claude and ACP stderr is logged by whole lines (`secrets/log-redaction.ts`), so `SB_CODEX_WIRE_LOG` frames and split stderr never log a value. **Approval cards**: `AgentApprovalBroker.open` refuses a draft whose detail, `hostWrite` or plan holds a live value of the chat's scope (`SECRET_IN_DRAFT_REFUSAL`) before the card is stored or published, since masking a stored plan would change what an approval runs. `pendingEvents` and `getPendingRequests` mask again on every recovery, and `respond` refuses to approve a card that still holds a live value (opened before the secret was saved): it can only be denied. A hit posts one `SECRET_MASKED_TEXT` system row per turn (a changed-file hit names the file). It cannot change what the model saw or the provider's transcript. **Usage counts** (`main/secrets/secret-analytics.ts`, closed list in `shared/analytics-envelope.ts`; buckets only, never a name, title, instructions, value or length, checked by the canary test): `secret_request.opened` (agent kind, ttl, remote) and `refused` (plan, child, cap, invalid; an archived chat is not counted) from the tool; `answered` (saved or declined, time bucket) and `closed` for a card that ends unanswered (expired, withdrawn, archived) from `reportSecretCard`; `closed` for a saved file that ends (expired through the store's `onExpired`, deleted by Delete now, archived per live file); `extended` (how many times this secret, counted in memory per backend run); `masked` with the masked row, so once per turn plus once for a changed-file hit at turn end. The headless server configures no analytics, so a remote backend sends none yet. The collector (tn07-site analytics Worker) must list these events and properties before it accepts them.
- **Visual preview** (flag `agent_visual_preview`, off; `visual-preview-tool.ts`, rules in `shared/visual-preview.ts`). With the flag on and a renderer set, every chat gets `preview_visual` (read-only, no card in any mode) and the `VISUAL_PREVIEW_INSTRUCTIONS` paragraph (preview a complex html-live page once before posting it, only then). Arguments: `block` (one whole fence) or `body` plus `kind`; the chat's caps and a chart's spec are checked before anything renders, and a bad argument costs nothing. At most 5 a chat per turn (`VisualPreviewTurnCounter`, reset on `turn.completed`), 20 s each, then an error result. The desktop sets the renderer (`main/preview/visual-preview-host.ts`, called from `registerHtmlPreviewHandlers`): it pushes `visual-preview:request` to its window and takes `visual-preview:result` only from that window. The headless server never sets one, so the tool and its paragraph are absent there (a remote chat has none). The result is an MCP `image` content block plus a text part, so `McpToolResult.content` holds images too.

- **Instinct bridge read tools** (flag `instinct_bridge`, off; `bridge-tools.ts`, service `main/bridge/read-service.ts`, allowlist `main/bridge/allowlist.ts`). With the flag on every chat gets `list_projects`, `list_recent_chats`, `search_chats` and `read_chat` (read only, no card in any mode); the list is built when the agent's bridge connects, and each call reads the flag again and answers `bridge_disabled` once it is off. Answers are JSON text, errors the `BridgeError` shape with `isError` (a thrown error is `internal_error` with a fixed message; the detail goes to the log only). Every answer covers only the projects the owner checked in Settings > Labs (`bridge:*` channels, `admin` scope, so no phone writes the allowlist; a policy row per checked project under its realpath with the default policy, deleted by id on uncheck and with its project on `removeProject`; none by default; a policy no sidebar project resolves to serves nothing and is listed there as an orphan to remove) on this desktop's machine id (`hubInstallId`). The allowlist is applied in SQL before ranking and limits on the FTS and the fallback path (`searchMessagesInDatabase`'s `projectPaths` scope; global search passes none and is unchanged), and title matches (`searchChatTitlesInDatabase`, the same word-prefix and archive rules) merge with message hits into one row per root chat with `matched_on` (`onePerChat` keeps each chat's best hit before the limit, from at most 1,000 candidates; titles are matched after `maskStoredText`). Snippets are plain text, 240 characters at most, masked with `maskStoredText`; `read_chat` reads `loadConversationHistoryWindow` (masked), the registry's pending requests and live status, and pages with an opaque `since` cursor bound to the chat, machine and policy revision, whose key covers status, the newest message, the latest reply's text, pending requests, archive state and title (`unchanged: true`, or `cursor_expired`). Chat and project labels resolve exact id, then exact normalized label, then word-prefix fuzzy (`bridge/resolve-label.ts`); two plausible matches are `ambiguous_target` with choices. No answer carries a local path. Lists are local only for now (`partial: false`, no unavailable machines) and evidence is `not_measured`.
- **Instinct bridge delivery tools** (same flag; service `main/bridge/delivery-service.ts`, host built by `ProviderRegistry.bridgeDeliveryHost`). Beside the reads every chat gets `start_chat`, `send_to_chat` and `stop_chat`, no card in any mode. The caller is the chat the MCP token names (`BridgeCaller`, the owner for now): from plan mode it can only stop, and it starts or drives no chat in a mode wider than its own or the project cap (`mode_not_allowed`, never lowered silently for an explicit mode). Each call reserves `(operation, local:<caller root>:<idempotency_key>)` with its input hash in `bridge_calls` before any provider action; a replay answers from the record after checking the project is still allowed and settles a call a crash left mid-way from `mobile_turn_acceptances` (`turnAcceptanceStateByOrigin`). Messages are ordinary user turns through `submitManagedUserTurn` with origin `bridge-<call id>` (chat row `remote_bridge-<call id>`), never `deliverPeerMessage` or its peer gate, and never decline an open card. A start creates the chat, its mode, model and `bridge_origins` row before `startManagedSession`; one bridge group per machine (a start in flight or a busy bridge-origin chat refuses a second start with `policy_denied`). A send resumes a dormant chat with the phone's resume options and picks the delivery with `peerDelivery` (it submits `queue` for an idle chat, so a turn that began meanwhile never gets an unrequested steer). A stop bumps an in-memory per-chat fence before any await, cancels only `remote_bridge-` queued rows, then runs `interruptChat` (the INTERRUPT handler: hub children, auto-resume disarm, stop during start) again every 200 ms until the chat has no turn and no start left: the Claude adapter ignores an interrupt before its query exists, so one Stop right after a start would be lost. It answers `stopped` only then (a turn running or being prepared, `host.running`; the owner's held queued messages do not count), and `stop_unconfirmed` after 20 s or when a queued bridge message could not be taken back. Bridge-queued messages are cancelled on every round, and a send that ended `delivery_unknown` after a stop is stopped too. Before each submit the flag, the project's policy (root and mode cap) and the archive state are read again, and a dormant chat's folder is checked before the resume starts it. A bridge steer goes through `submitManagedUserTurn(..., { steerFallback: true })`, which queues it at the adapter boundary when it can no longer land, and the receipt reports `queue` when the registry queued the message. A steer waits for the provider's first event and first reply (`firstEventSpans`, `firstContentSpans`): before that it queues, since an adapter whose provider has not taken the first turn runs a steer as a turn of its own. `start_chat` saves the account the start resolved to (`setConversationProviderInstanceId`), as a client does for a new chat, so a resume after a restart uses the same account. The execution root is realpathed under the policy root before each submit.
- **Instinct bridge device link** (same flag, plus enrollment; `main/bridge/device-key.ts`, `relay-client.ts`, `device-link.ts`). Settings > Labs (`bridge:device-status`, `bridge:enroll-device`, `bridge:set-device-label`, `bridge:remove-device`, admin scope) makes one ECDSA P-256 key per installation for machine id `hubInstallId`. The private key is stored in the settings row `bridge.device` (admin-only family) only as `\0SBE` plus the `safeStorage` ciphertext; with no keychain it is not made, and a row this build cannot read is never overwritten. `BridgeDeviceLink.reconcile` (startup, the `labs.instinct_bridge` setting, enroll and remove) runs one `BridgeRelayClient` only while the flag is on and a key exists. The client dials `wss://<origin>/connect` (`https:` only, `http` loopback only from `SB_BRIDGE_RELAY_ORIGIN`, TLS checked, `User-Agent: Switchboard/<version>`), signs `bridgeHelloPayload` (nonce, machine id, origin, wire version 1), sends `bridgeCatalog` (project id, label, default agent, agents, mode cap; never a path) after the welcome and on every allowlist change, pings every 30 s, and reconnects with backoff (30 s to 5 min after a relay refusal). It keeps the welcomed connection generation, refuses a welcome at or below an earlier one, and drops any frame tagged with another machine or generation. It runs no command in this release: a command frame is logged with `commands_disabled` and dropped. The relay side and the operator endpoints are in tn07-site `workers/bridge-relay`; `scripts/bridge-operator.mjs` enrolls, lists and revokes with the operator key.
