# Switchboard MCP server

Detail for this part of the code. The root `AGENTS.md` holds the rules that apply everywhere (shipping checklist, cross-surface policy, logging, writing style); they apply here too.

## Switchboard MCP server (`src/main/mcp/`, agent tools for all three agents)

One MCP server per backend process gives Claude, Codex and OpenCode the same tools, and is the ONLY gate for them. Verified live against the CLIs (2026-09-27): Claude routes an MCP tool through `canUseTool` and asks nothing else; Codex (sandbox) confirms a non-read-only tool with a yes/no `mcpServer/elicitation/request`, never in full access; OpenCode never asks for an MCP tool unless the user's own config says so, and its plan mode is the model obeying, not enforcement. So the server enforces plan mode, the approval card, the budget and the link check itself.

- **Transport.** `stdio-bridge.ts` holds a dependency-free CommonJS bridge that `ensureStdioBridge` writes to `<userData>/mcp/switchboard-mcp.cjs`; each agent spawns it (`process.execPath` with `ELECTRON_RUN_AS_NODE=1`, so the Electron binary or the headless server's node) as its `switchboard` MCP server. The bridge dials the backend's `127.0.0.1` listener (`switchboard-mcp-server.ts`), sends `{ switchboardMcpAuth: <token> }` first, then pipes. The token is read from a 0600 file under `<userData>/mcp/tokens/` named by `SWITCHBOARD_MCP_TOKEN_FILE`, never passed as a value: Codex's `-c` and Claude's `--mcp-config` put the server's env on a command line any local user can read with `ps`. Kept as source rather than a second bundle so a provisioned VM needs nothing extra. The protocol (initialize, ping, tools/list, tools/call, notifications/cancelled) is hand-rolled in `mcp-session.ts`; `@modelcontextprotocol/sdk` is only transitive here.
- **Token = identity.** `ProviderRegistry.openSwitchboardMcp` mints one per session start (`mcp-tokens.ts`, sha256 in memory), and the tools are built for THAT thread; `STOP_SESSION` revokes it, deletes its file and drops live connections. The mode the gate reads is the adapter's own (`ProviderAdapter.runtimeModeOf`), because a queued message's mode applies only when it starts. Links and the budget key on `resolveRootThreadId`. A registry built with injected adapters (tests) gets no server unless one is passed as the 5th constructor argument.
- **Registration** (`agent-registration.ts`, pure): Claude via the SDK's `mcpServers`; Codex via `-c mcp_servers.switchboard.{command,args,env,tool_timeout_sec}` on its per-chat `app-server` (raised to 180s: no call waits on a card any more, but a full-access create makes several host calls with no card, and Codex gives up after 60s by default); OpenCode via ACP `session/new` `mcpServers`. User MCP servers keep loading from their own config.
- **No second prompt, only when OUR server was registered**: Claude's `canUseTool` allows `mcp__switchboard__*`, Codex's confirm for `serverName: 'switchboard'` is accepted, OpenCode's permission for `switchboard_*` is allowed. Without a registered server those names get the ordinary policy, so a user server that calls itself `switchboard` is not trusted.
- **Tools.** Reads, no card: `get_pr_status`, `list_pr_conversations`, `get_pr_diff` (pages of at most 60 KiB, `mcp/pr-diff-page.ts`). Writes, one card each: `reply_to_conversation` (text, optional `resolve`), `resolve_conversation`, `rerun_check` (GitHub Actions only), `comment_on_line` (one inline comment, the line must be in the fresh diff), `draft_review` (summary plus up to 30 comments, 40 KiB; one write against the budget). Never merge. A verdict is never the agent's: `draft_review` has no verdict argument (one sent is refused, `shared/agent-pr-review.ts`), the card preselects none and offers only what `reviewEventsFor` allows (an author or a closed PR gets Comment only), and an answer without a verdict posts nothing. `create_pull_request` (one card: editable title and description, the repository and "source -> target"; rules in `shared/agent-pr-create.ts`) is the one write that needs no linked PR: it opens one on the repository the chat's `project_path` points at (any other `repository` is refused), from the session cwd's current branch (`pull-requests/branch-check.ts`, which also refuses a branch `git ls-remote` does not find on that repository's remote) into the host's default branch unless given. For a project folder that holds several repositories, optional `repoPath` (relative to the project folder or absolute) names one: `resolveRepoDir` (`pull-requests/project-repos.ts`) realpaths both sides and refuses anything not inside the folder (the folder itself allowed, so no `..` or symlink escape) or not a git work tree. A folder outside (a worktree in /tmp) is accepted only when it is a linked worktree of a repository whose main checkout is inside: its `git rev-parse --git-common-dir`, realpathed, must be a `.git` folder inside the project folder, and that main checkout's `git worktree list` must hold it, so a hand-made `.git` file does not count. `mainRelPath` names that main checkout; in a project that is a repository a `repoPath` must be its own checkout or a worktree of it (`mainRelPath` '.'). Its remote is the repository (a `repository` given too must match it exactly, `repoPathRepositoryProblem`) and must be one the project covers (see Chat ↔ PR links), and the branch checks run with it as the cwd. Without `repoPath`, a parent folder plus `repository` picks the ONE child work tree whose remote matches (`findChildRepo`), refusing zero or several with the candidates listed; the chat's own checkout wins when it is that child or a worktree of it (it is the source branch then, and it settles several matches), and with neither argument the chat's checkout alone picks its child. A refusal that a new checkout could change (no children, no match, several) is tried once more against a fresh scan. The card shows that path (`create.localPath`), desktop and plain-text detail only: it is not in `hostWritePreview`, so the phone digest and its pinned vectors are unchanged (the repository is already in `target`). An OPEN PR for the source branch is linked and returned instead, before the card and again in `PullRequestService.createPullRequest`. Optional `reviewers` (at most 10 logins, display names or emails; GitHub teams as `team:<slug>`) are matched before the card against `PullRequestService.reviewerPool` (the Reviewers card's candidates plus the signed-in user) by `shared/agent-pr-reviewers.ts`: exact, case and a leading `@` aside, on id, login, display name, a listed email or a team slug; without an exact match the ONE person whose id, login, display name or team slug holds the name (or is held by it) is taken, and the card shows who; a shared word or an email domain never picks anyone. A name matching several people, several close ones or nobody, or the signed-in user, is refused with the candidates listed. The card lists them (`create.reviewers`), removable on the desktop; the approval sends the kept ids. Bitbucket sends them in the same POST (`reviewers: [{uuid}]`); GitHub creates the PR and then posts `requested_reviewers`, and when that second call fails the PR stays (`OpenedPr.reviewerFailure`): the agent gets the URL and the reviewers that failed, and the create is never re-sent. `draft` is GitHub only and refused on Bitbucket. After a create it links the PR to the ROOT conversation (source `created`, which relinks a tombstone) and emits `pull-requests:links-changed` with `created: true`, which marks the Reviews list stale (`review-store.markStale`). An `offline`/`unknown` failure is uncertain: it looks for the PR once, and otherwise tells the agent not to create again. The MCP server's instructions tell agents to use it instead of `gh pr create`, bbpr or a host API. Link tools, no card (`mcp/pr-link-tools.ts`: a link changes only what these tools may act on, nothing on a host): `link_pull_request` (a URL, or `repository` + `number`; the `pull-requests:link` repository rule; source `agent`) and `unlink_pull_request` (tombstones, like Reviews' Unlink), both denied in plan mode through `decidePermission`, and `list_thread_pull_requests` (each link's source and last known state, plus the chat's last automatic linking failure), which runs unasked. Plus the two session tools. Every other tool acts only on PRs linked to the calling chat (`pickLinkedPr`), through the same `PullRequestService` as the human writes (`setAgentPullRequestAccess`, set in `registerPullRequestHandlers`), so its re-reads and validation apply.
- **Modes.** Plan denies a host write without a card. Full access STILL shows the card: posting as the user on GitHub or Bitbucket is not a local edit (`hostWriteGate`). Sandbox, accept-edits and auto show it. The one exception is `create_pull_request` (`createPullRequestGate`): full access opens the PR without a card, because the user asked for it, it merges nothing and closing it undoes it. It still counts against the budget and still carries the via-Switchboard marker.
- **The card does not hold the turn** (`mcp/agent-approvals.ts`, rules in `shared/agent-approval-cards.ts`). It is a `request.opened` with a `hostWrite` payload (`shared/agent-host-writes.ts`) and a plain-text `detail` for clients that do not render it; ids start `sbmcp_` and `RESPOND_TO_REQUEST` routes them to the broker, with an optional 4th argument `{ text, resolve, quiet, ... }`. The tool returns AT ONCE, not as an error: "Queued for the user's approval (card <id>) ... Do not send it again." The card is stored with the write it would run as data (`plan`: `PrWritePlan` in `pr-tools.ts`, `PeerSendPlan` in `peer-mcp-tools.ts`) in `agent_approval_cards` (`db/agent-approval-cards.ts`, keyed by the ROOT conversation), so it waits until the user answers or the chat ends and survives the turn ending, a profile switch or relocation (the internal `stopSession` leaves it) and a backend restart (the broker loads the table, parsing each row on its own: a row it cannot read is deleted and its chat gets a failed result row, so one bad row never drops the rest; `getPendingRequests` serves the broker's cards, not the registry's per-turn record, so a `status: error|stopped` cannot drop them). It closes exactly once (`ApprovalCardBook.take`): approved, approved quietly, denied, dismissed (a quiet deny), withdrawn by the agent (`withdraw_approval`, its own chat's cards only), or closed by the user's `STOP_SESSION` or an archive (`closeAgentCards`). The one time limit is a safety cap: a card unanswered for 7 days (`AGENT_CARD_MAX_AGE_MS`) closes unsent (`expireOld`, run at startup and whenever a card is opened, recovered or answered; outcome `expired`, the agent is not woken), and every card says so (`AGENT_CARD_LIFETIME_TEXT`: appended to the plain-text detail, and a line on the desktop, Expo and Android host-write cards). `notifications/cancelled` or a dropped connection no longer touch a card: the agent has already moved on. Only an approval runs the write (`runPrWritePlan` / `runPeerSendPlan`), with every check after the card that ran before: plan mode, the PR link, the project's repository, the edited text, a phone's `shown`, and for a peer send the whole `deliverPeerMessage` path (link rules, budget, refund, Not delivered row, the re-check after the checkpoint). `reply_to_conversation` with `resolve` stays ONE card that does both. The text the user leaves in the card is what is posted, ending with a `via Switchboard` line (`withViaMarker`). Then `reportAgentCard` stores a `[[sb:approval-result]]` system row under the root id (`ApprovalResultRow`, desktop `ApprovalResultRow.tsx`, both phones show `approval.result` and the stored row as a notice) and, unless quiet, delivers the result to the agent as a turn of its own (`approvalResultTurn`): a new turn when idle, `delivery: 'queue'` behind a running turn (the `QueuedTurnLedger` path), or held in `agent_approval_results` and sent when the chat's session next starts (a result answered during a profile switch or relocation is held too, and `flushHeldApprovalResults` sends it once that move commits or rolls back). That turn is wrapped in `<switchboard-approval-result>`, says it is from Switchboard and carries no authority, and every surface's synthetic split drops it (`synthetic-message.ts`, Android `SyntheticUserMessage.kt`), so the row is what the user reads. **It is not a user turn**: `sendApprovalResultTurn` sets no `turnDepth`, renews no link and clears no plan, so a result can neither restart a peer chain nor spend or refill a link's budget (`agent-approval-results-registry.test.ts`). A call still sends `notifications/progress` every 10s when the client gave a progress token, now only for slow host calls a full-access create makes without a card: OpenCode's MCP call timeout is 30s and not settable over ACP.
- **Phones** approve a host write card as drafted: a device with the `chat` scope (a phone) may approve, because it can already send the agent full-access turns, which is the larger power. The Reviews write channels (`PullRequestWriteChannels`: merge, the user's own comments and reviews) stay `admin`-scoped, except the subset a desktop-granted `pr-write` phone may call (see `src/main/pull-requests/AGENTS.md`, Phone writes). The backend advertises `agent_host_write_phone_approval_v1` (`shared/host-write-phone.ts`); a phone without it offers Deny only, since an older backend refuses the approval. The phone card (`phoneHostWriteButtons`, ported to Android as `HostWriteCards.kt`) shows everything the approval posts, uncapped, from the card payload (`hostWritePreview`: title, description, reply, summary, every review comment under its `path:line`), never the capped plain-text detail; a long draft starts collapsed and no button approves until it is opened, and a payload the phone cannot show in full (null preview) is Deny only. A create's reviewers are a `Reviewers` section of that preview (one `Display (login)` line each), so the digest covers them and a phone approves all of them. It has an action-named button, and for `draft_review` one button per offered verdict with none primary. It never edits: the registry passes only `resolve` and `verdict` (`approvalChoiceOnly`) from a device without the `admin` scope, so a phone's approval posts the draft it showed. It must also carry `shown`, the `hostWriteShownDigest(requestId, card)` of the draft it rendered in full: FNV-1a 64 over the request id, the card's `target` (host, repository, PR number; for a create, the source and target branches), the action and exactly what `hostWritePreview` shows, so the same text on another card or PR does not match. Ported as `HostWriteCards.shownDigest`; two cross-implementation vectors are pinned in both test suites. The broker recomputes it from its card and refuses a missing or different one ("Update the Switchboard app..."), so a build that showed the capped detail cannot approve. The desktop needs none. Deny never needs it. **Editing an agent draft on the phone before approving is deferred** (the user, 2026-09-29: not a priority). The design when it comes: the phone sends its edited text (and kept reviewers), `approvalChoiceOnly` lets those fields through for a `chat` device, and `shown` is computed over the edited text rather than the card's, so the broker can check the phone approved exactly what it will post. The broker refuses a review approved without a verdict the card offered (`hostWriteApprovalProblem`) and keeps it open, and logs which device approved (`describeRequestClient`). Every other guard (the re-checks after the card, plan mode, budget, link rule) is unchanged. The peer-send card stays answerable from a phone, as before. No client expires a card on its own (only the backend's 7-day cap closes one), so an hours-old card recovered through `GET_PENDING_REQUESTS` renders and answers like a new one. On a backend advertising `agent_async_approval_v1` (`AGENT_ASYNC_APPROVAL_CAPABILITY`) both phones offer "Don't wake the agent" on a server card (`offersQuiet` / `quietly` in `apps/mobile/src/lib/approval-actions.ts`, `ThreadInteractionPolicy` on Android): it adds `quiet: true` to the same response (Approve becomes "... quietly", Deny becomes Dismiss), and `approvalChoiceOnly` keeps it for a `chat` device. An older phone simply never sends it.
- **Guards**: 10 writes per chat per 10 min, counted when a write reaches its card (the cap is checked first, so a refused card costs nothing); at most 20 OPEN cards per chat (`AGENT_OPEN_CARD_CAP`), past which a new ask is refused with `isError` and told to wait or withdraw one; reply text capped at 8,000 chars; every refusal is tool output with `isError`.
- **Known limit: a write in flight is not atomic with its checks.** Every write re-checks the link and the mode after the card and again before a second write (reply, then resolve), and a peer send re-checks the mode after its card. An unlink, cancel or stop that arrives after the last check cannot stop a host call that has already started. An uncertain result tells the agent not to post again; there is no host-side dedupe key. Since a card can now be answered hours later, the PR the card shows may have moved on (new commits, a resolved thread): the host call itself refuses a stale target where it can (the service re-reads before a write), but the card's quoted text and diff excerpt are as of when it opened. A result turn the adapter refuses is held and retried at the next session start, not retried in place.
- **Child chats** (flag `hub_children`, off; `hub-tools.ts`, runner `main/hub/hub-start.ts`). With the flag on, a chat that is not an open child gets `start_children` and `list_children` and the `HUB_INSTRUCTIONS` paragraph (`SwitchboardMcpServer.open`'s 3rd argument). The batch card is an agent card with a `HubBatchPlan` (`request.opened.hubBatch`, desktop `hub/HubBatchRows.tsx`, plain `detail` elsewhere); only plan and sandbox ask (`hubNeedsCard`), plan itself is refused, and above them the batch starts at once with an approval-result row. Approval re-checks the parent's mode and the disk. Children start through `startManagedSession` and `submitManagedUserTurn`, which skip the `child_read_only` gate that `submitClientUserTurn` and `SEND_TURN` apply. The bridge sends its parent pid (`agentPid`) on auth, so `hub-measure.ts` can sample each agent's process tree. **Dependencies** (`main/hub/hub-deps.ts`, links in `main/git/dependency-links.ts`): every `node_modules` next to a `package.json` (3 levels) and each `worktree.link` path of the launch config is linked, cloned, installed or left out per `hub.childDependencies` and the rules L1 to L5 in the module header, before the brief. A link is an absolute symlink listed in the shared `info/exclude` (no trailing slash: a `.gitignore` line like `apps/mobile/node_modules/` does not match a symlink) and in `switchboard-dep-links.json` in the worktree's git folder, which `removeWorktree` reads to unlink first. After each child turn `checkChildDeps` compares links, the child's lockfile and the install record (`.package-lock.json` and kin) with link time; a change stops the child (`HubStartHost.stopChild`, the user's Stop) with one `blocked` wake. An open child gets `own_dependencies` (`buildChildHubMcpTools`), which swaps each link for a clone made beside it. `FilesChannels.WRITE_FILE` and `DELETE_FILE` refuse a path under a tracked link (`linkedDependencyAt`); agents' own file tools are not checked. **Desktop UI**: `ProviderRegistry.hubView` serves `provider:hub-list-children` (the chat, its parent while it is an open child, its unsettled children with `childState`, and `parentState`), and `hub.children-changed` (the parent's root id) fires on `HubStartHost.changed` and on a child's status, turn end, card or limit event (`HUB_VIEW_EVENTS`). Session rows carry `hub` from `withHubFields` (`ipc/app.ts`, flag on only); the sidebar nests with `nestHubChildren`. Renderer: `stores/hub-store.ts` (views of mounted chats only), `components/hub/` (chip, strip, child banner, Nudge as a `To: <child>` chip in the parent's composer). **Messages** (`peer-mcp-tools.ts`): a parent and its open child share a lineage edge, so `send_agent_message` between them opens no card except that plan denies it, and with the flag on the tool takes `delivery` (rules in `src/main/provider/AGENTS.md`, Cross-session messaging). **Reports and wakes** (`main/hub/hub-wakes.ts`, `main/hub/hub-read.ts`): an open child gets `report_to_hub`; the registry stores each call as a `hub_wakes` row (summary, and a pointer whose `toolCallId` is the oldest unclaimed `tool.started` of that tool on the thread, plus `transcriptPath` from `transcriptPathOf`, the current provider's newest transcript), never the report. `HubWakeScheduler` sends a parent's wakes as one `<switchboard-hub-update>` turn through `sendApprovalResultTurn` while it is idle (status `idle`, nothing preparing or outstanding, no switch), 15 s after the newest; a wake is delivered (revision = send time) only on the agent's first output on that turn (`content` other than the compaction notice, or `tool.started`; never `status: running`, which every adapter sends itself inside `sendTurn`), and a refusal, a turn that ends or stops without output, or 2 minutes with none (the turn is interrupted) counts as a failed try; two, or 30 turns in an hour, set `hub_parents.held` until Deliver (`provider:hub-deliver-held-wakes`) or the user's next turn to the parent, which carries every pending wake (`claimForTurn`, marked delivered in the turn's own commit next to fork merge-backs, `joinDispatched`). Every delivery stores a `[[sb:hub-update]]` row (`formatHubUpdateMarker`, desktop `hub/HubUpdateRow.tsx`) in the transaction that marks its wakes delivered (`HubWakeHost.commitUpdate`); when that write fails, the wakes stay out of later sends and the write is tried again (in memory, so after a restart they are sent once more). The send counter is in memory, so a restart starts a new hour. The update block goes in front of the user's words (`withMergeBacks`), since the synthetic split drops leading blocks only. The parent gets `read_child` (own children only, any phase), which loads through `loadConversationHistory` (a missing pointer file is reported only when that history is empty); a Codex or ACP child's tool calls come from the SQLite copy, which keeps at most 32 KiB of a report. The hub view carries `heldUpdates` even after every child settled, so Deliver stays reachable. **Stop** (`main/hub/hub-stop.ts`, registry `stopHubChild` and `stopHubChildren`): `INTERRUPT` on an open child stops it like `interrupt_child` does, and on any other chat it also stops every open child in parallel (`hub.stop` perf line), sets `hub_parents.held` (reason `stop`) and disarms the auto-resume rows (`stop`, `parent_stop`, `interrupt_child`); `provider:hub-stop-children (parentId, childId?)` is the strip's Stop all (and later the phones'). One child's stop (a running subagent counts as running) disarms its resume, closes its agent cards, expires its provider requests, cancels its queued messages and counts its running subagents as failed. A running child stopped by the user or with its parent gets one `stopped` wake (held under a held parent); `interrupt_child` (parent tool, denied in plan mode, own open children only) writes none, and stopping a child with no running turn is a quiet success. The hold lifts on Deliver, on a user turn that carries the wakes, or on one that carries none (`HubWakeScheduler.liftHold`, `SUBMIT_USER_TURN` only, like the carrying). Switchboard writes its own wakes once per task (`ChildTaskNotes`: a brief or a parent message is a task; a report, or one such wake, uses it up; a child with no task in this process gets none): decided at the turn end, since adapters send the `error` before the end that carries `limit`: an end with `limit.limitClass: 'context_full'` is `blocked`, a usage limit writes nothing, an end after an `error` (or a `status: error` the agent's process gave) is `failed`, and an end with nothing outstanding and no subagent running, or a clean process exit, is `stopped` ("Ended its turn without a report."). A session end Switchboard caused (its own stop, a profile switch, `stopAll`) writes none. A child still `starting` that is stopped gets no first turn (`HubStarter.cancelStart`): it becomes `failed_start` with a `stopped` wake. `NativeSubagents` counts each thread's top-level Agent/Task calls until their result (a background agent until its `task.notification`); a child with one running is Working in the hub view, and `list_children` reports `nativeSubagents { running, done, failed }`. **Idle reaper** (`HubIdleReaper`, a 60 s tick, production registries only): an open child whose last wake is `report`, idle (status idle, nothing preparing or outstanding, no request, no switch) with no subagent running for `hub.idleReapMinutes` (20, off allowed) since its last turn end, has its session stopped (`stopChildSession`, which keeps the lineage edge) and then every process of its agent's tree that is still alive gets SIGTERM and, 2 s later, SIGKILL (the tree is read with `ps` before the stop, from the bridge's `agentPid`). The registry keeps its start options with the resume id (`reapedChildren`, in memory), and `deliverPeerMessage` from its parent starts the session again before it delivers (`hub.resume-reaped`). `hub.reap` logs each reap (idle minutes, processes, killed). **Limits** (needs `limit_auto_resume` too): `LimitResumeHost.limited` gives an open child's parent one `limited` wake per limited turn end (and one when a re-arm gives up), with `limitStateText` as the summary; `changed` with `resumed` gives a `resumed` wake. The fire reads `childFireContext` (settled, parent held, run slots: open children whose status is `running` or that prepare a turn (not `hasOutstandingTurn`, which counts held messages), a resume on its way, and a move in progress, keyed by the account the session runs on), and a `no_slot` wait is retried by `slotFreed` when any session stops running (plus the 5-minute timer); the hub view shows it as Starting, waiting for a slot. `move_child` (`ProviderRegistry.moveHubChild`, rules in `moveChildProblem`) needs a live child session that runs no turn and holds no queued messages, and refuses every ACP agent, before anything changes (the switch would refuse both after the disarm): it reads the target's usage unforced (a forced Claude read can prompt for the keychain), disarms with `moved` BEFORE it calls the SWITCH_INSTANCE handler (`instanceSwitcher`), so no timer resumes the session being switched, then sends the resume turn itself (no `limit-resume` row and no `resumed` wake: the parent did it). From the slot check to the resume turn the child holds the target's slot (`movingChildren`), since the switch's own stop frees slots for waiters. `list_children` adds `accounts` while a child has a `limit_resumes` row.
- **Secret requests** (flag `agent_secret_request`, off; `secret-tools.ts`, rules in `shared/agent-secret-request.ts`, files in `main/secrets/secret-store.ts`). With the flag on every chat but an open child gets `request_secret` (the tool still refuses a child) and `SWITCHBOARD_SECRETS_DIR` (its 0300 folder) in the agent's env at session start; Codex also gets it through `-c shell_environment_policy.set`, since its default excludes drop any name holding SECRET from commands. The card is an `sbsec_` card in the same broker with a `SecretRequestPlan` (no value) and `request.opened.secretRequest`; its `detail` and push text never carry the title or instructions. Only `ProviderRegistry.answerAgentSecret` saves (it checks the answer's shape): the broker's `saveSecret` takes the card out of the book and its table first, then runs the store write, in one synchronous step; a failed take writes nothing and a failed write puts the card back. `RESPOND_TO_REQUEST` may only deny one. A Stop keeps the card and the files (`closeChat` skips them); every archive (the sidebar, a kanban card moved to Done) runs `notifyConversationArchived` through `db/archive-events.ts`, which closes the card and deletes the chat's folder, and the store's sweep deletes what an archive left. On the headless server the result names the machine (`setMachineLabel`). The ACP `fs/write_text_file` handler refuses a path under `<userData>/secrets`. Errors from the store are logged as codes only, since an fs error message holds the path. **Answer channel** (`AgentSecretChannels`, `agent-secret:answer|extend|delete|list`, capability `agent_secret_request_v1`): registered in `registerIpcHandlers`, so an SSH chat's answer reaches its own backend through the tunnel. The `admin` scope gates it (`device-auth.ts`), so no phone can call it. Every handler checks its argument shapes (`isAgentSecretAnswer`: exactly `{ save: string }` or `{ decline: true }`) and refuses everything while the flag is off. Extend and Delete now act only on a secret of the asking chat's root id. LIST answers metadata and a `status` (`live`, `expired`, `deleted`), never a value. `carriesSecretArgs` keeps these calls out of the perf spans and out of `WsTransport`'s reconnect queue; no host logs request arguments. Desktop UI: `renderer/components/chat/SecretRequestCard.tsx` (uncontrolled password input, keys stop at the card and `App`'s shortcut handler skips them) and the pure rules in `secret-request-card-model.ts`. The card's result row (`apr_sbsec_...`) replaces the card and renders as its one-line state. **Phones** (Expo `SecretRequestItem` and `SecretLine` in `screens/ThreadFeedItems.tsx`, Android `SecretRequestRow` and `SecretRequestCards.kt`) are read-only: the card with Decline, which goes over `RESPOND_TO_REQUEST` as a deny, only when the backend has `agent_secret_request_v1` (else the plain approval with its `detail`), and the result row as one line (`secretResultLine`, also in `systemRowView` and `SystemMarkers.kt`, fixture `system-marker-cases.json`). Phones never parse a URL (`secretInstructionParts` splits the host by pattern; the phone runtimes do not all have `URL`). **Redaction** (`main/secrets/secret-redactor.ts`, the backend's one `secretRedactor`): the store arms a value on save and reads live files back in its sweep (so at start), and drops and zero-fills it on every delete; values under 8 characters are not matched. Three hooks mask the exact, base64, base64url and URL-encoded forms as `[secret NAME]`: `ProviderRegistry.publish` (every runtime event, through `RuntimeEventRedaction`, which holds back the last longest-pattern-less-one characters of a streamed message until the thread's next event; changed-file cards go through its `mask` and get `noRevert: 'unknown'`), `db/secret-mask.ts` (`maskStoredText`, used by every writer of message text, so every row and the FTS index; a fork's scope adds its fork ancestors' secrets), and `conversations/history.ts` (every history read; the memo keeps the unmasked read). A hit posts one `SECRET_MASKED_TEXT` system row per turn (a changed-file hit names the file). It cannot change what the model saw or the provider's transcript.
- **Visual preview** (flag `agent_visual_preview`, off; `visual-preview-tool.ts`, rules in `shared/visual-preview.ts`). With the flag on and a renderer set, every chat gets `preview_visual` (read-only, no card in any mode) and the `VISUAL_PREVIEW_INSTRUCTIONS` paragraph (preview a complex html-live page once before posting it, only then). Arguments: `block` (one whole fence) or `body` plus `kind`; the chat's caps and a chart's spec are checked before anything renders, and a bad argument costs nothing. At most 5 a chat per turn (`VisualPreviewTurnCounter`, reset on `turn.completed`), 20 s each, then an error result. The desktop sets the renderer (`main/preview/visual-preview-host.ts`, called from `registerHtmlPreviewHandlers`): it pushes `visual-preview:request` to its window and takes `visual-preview:result` only from that window. The headless server never sets one, so the tool and its paragraph are absent there (a remote chat has none). The result is an MCP `image` content block plus a text part, so `McpToolResult.content` holds images too.
